# 審查流程：AI 交叉審查＋人工合併

## 1. 原則

- **寫程式的 AI ≠ 審查的 AI**：同一個工具（甚至同一個模型的另一個對話）不能審查自己寫的程式。
- **AI 審查是過濾，人類核准才合併**：AI 找問題，人類做決定。
- **審查依清單**：每次審查都要跑通用清單＋該變更領域的專用清單，不靠臨場發揮。

## 2. 工具分工

| 實作者 | 第一審查者 | 第二審查者（🔴 才需要） |
|---|---|---|
| Claude Code（Claude Pro） | Gemini（Google AI Plus）新對話：一般審查（審查提示詞 §1） | Gemini **另一個**新對話：規則與安全專審（審查提示詞 §5），看不到第一份報告 |

- 2026-11-25 依實際工具調整：實作只用 Claude、審查只用 Gemini（見 `docs/prompts/AI工具與上下文.md`）。

- 每個 PR 在說明欄記錄「實作工具」與「審查工具」。

## 3. 風險分級

| 等級 | 什麼樣的變更 | 需要的審查 |
|---|---|---|
| 🔴 高 | `rules-engine`、`protocol`、`database` migration、事件儲存與快照、權限與 Token、覆寫、可見性過濾 | **兩份 Gemini 審查**（兩個不同的新對話：一般＋規則與安全，第二個看不到第一份報告）＋你核准；核准前隔天再看一次 diff |
| 🟡 中 | `server` 其他部分、`content` YAML、小遊戲計分、Godot 的 `Net`／`Store`／`Presenter` | 一個 AI 審查＋你核准 |
| 🟢 低 | UI 版面、美術、文字、文件、測試補強 | 一個 AI 審查＋你核准；小黃的 Godot 場景與美術 PR 由你核准，你的演出框架改動影響場景時請小黃看一次 |

- 🔴 路徑寫在 `.github/risk-paths.yml`；合併前由 `review-gate` 檢查審查是否齊全（GitHub Free 私有 repo 沒有分支保護，靠自律＋事後稽核，見 `docs/review/CI與分支規則.md`）。
- **2026-11-25 兩人團隊**：程式全部由你寫，沒有第二位工程師，所以「非作者核准」改由**不同廠商的 AI 獨立審查**（實作 Claude、審查 Gemini）補上；你是作者也是核准者，因此 🔴 變更一律等 CI 全綠＋兩份審查報告的每條意見都已處理才合併，不能跳過。

## 4. 流程

```
1. 開 Issue（需求 ID、範圍、驗收條件）
2. 實作 AI：計畫 → 人類確認 → 測試先行 → 實作 → 自我檢查（typecheck／lint／test）
3. 開 PR（照 PR 模板；附測試結果、未完成、需要決定的事）
4. CI 全綠（不綠不審）
5. 審查 AI：依「審查提示詞」＋清單輸出審查報告，貼在 PR 留言
6. 作者處理：每條意見標記「已修正／不同意（附理由）／開新 Issue」
7. 🔴 變更：第二個審查 AI 重跑
8. 人類核准 → Squash merge
```

## 5. 審查報告格式

```
## 審查報告
- 實作工具：Claude Code｜審查工具：Gemini（Google AI Plus）｜審查重點：一般
- 範圍：M3-R08 傷害管線（PR #42）
- 結論：需要修改／可以合併

| # | 嚴重度 | 檔案:行 | 問題 | 依據（文件章節或清單項目） | 建議 |
|---|---|---|---|---|---|
| 1 | 🔴 阻擋 | damage.ts:88 | 上限寫死 30 | 清單 R-07；規則優先序 §6 | 改讀設定 |

### 架構邊界檢查（AGENTS.md §3）：通過／不通過（列出違反項）
### 硬性禁止檢查（AGENTS.md §4）：通過／不通過
### 測試是否足夠：…
### 文件矛盾或需要企劃決定的事：…
```

| 嚴重度 | 定義 | 處理 |
|---|---|---|
| 🔴 阻擋 | 違反架構邊界、硬性禁止、規則錯誤、安全問題、資料遺失風險 | 必須修正才能合併 |
| 🟡 重要 | 缺測試、可讀性差、效能隱憂、設計文件沒寫清楚 | 修正，或開 Issue 並在 PR 說明 |
| 🟢 建議 | 命名、風格、可選的改善 | 作者決定 |

## 6. 人類核准者的最後檢查（5 分鐘）

- [ ] CI 全綠；沒有被跳過的測試。
- [ ] 審查報告的 🔴 全部處理。
- [ ] PR 改動符合 Issue 範圍，沒有夾帶其他修改。
- [ ] 規則類變更：隨機挑一個測試，對照設計文件確認預期值是對的（AI 可能寫錯測試又寫錯實作，兩者一致但都錯）。
- [ ] 沒有新的執行期依賴（或已有 ADR）。

## 7. 防止 AI 審查失效的做法

- 審查 AI **只拿到**：AGENTS.md、相關設計文件章節、清單、PR diff、測試結果；**不拿實作的對話紀錄**（避免被實作者的推理帶著走）。
- 要求審查 AI 對每一條「通過」也寫出檢查依據（例如「已確認 damage.ts 第 40～60 行沒有讀取時間」），避免空泛的「看起來沒問題」。
- 每週抽一個已合併的 PR，人工重審一次，記錄 AI 漏掉的問題，回饋到清單。
