## 1. 專案一句話

4 人約 2.5 小時的**沙發派對競技遊戲**：客廳大螢幕（Godot 主螢幕）顯示地圖與演出，每人用手機（網頁）操作；塔羅、星座、骰子、喝酒（酒精版）為核心；伺服器權威結算所有規則。

## 2. 真相來源（Source of Truth）

## 3. 架構邊界（違反即退件）

```
Godot 主螢幕（GDScript）──┐
手機控制器（React）───────┼── WebSocket(JSON) ──▶ 伺服器（Node.js＋Fastify＋ws）──▶ 規則引擎（純 TS）
管理後台（React）─────────┘                                │
                                                          └──▶ PostgreSQL（事件＋快照＋審計）
```

| 規則 | 說明 |
|---|---|
| B1 | **所有規則只在 `packages/rules-engine` 結算**。Godot、手機、後台不判定合法性、不計算結果 |
| B2 | 客戶端只送 Command；收到 Event／Projection 才更新畫面 |
| B3 | `rules-engine` 是純函式：不碰網路、資料庫、檔案、時鐘、`Math.random()`；時間與亂數由輸入帶入 |
| B4 | 協定只在 `packages/protocol`（Zod）定義一次；JSON Schema、TS 型別、GDScript 類別一律由程式產生，**不准手寫第二份** |
| B5 | 事件寫入 PostgreSQL 成功後，才能回覆 `command.accepted` 與廣播 |
| B6 | 不公開的資料在伺服器端過濾，**不准送到不該看的裝置再由前端隱藏** |
| B7 | 卡牌效果寫在 `content/*.yaml`，只能組合受控效果元件（`docs/design/效果元件對照表.md`）；特殊效果只能呼叫有測試的 TS handler，**MVP 只允許 2 個**（命定天罰、祭司大招），新增要開 ADR；**禁止 `eval`、動態程式碼** |
| B8 | 依賴方向：`server → rules-engine → (無)`；`godot-client` 只讀 `protocol-codegen` 的產物，不匯入 TS |

## 4. 硬性禁止（Hard Constraints）

1. 禁止 `Math.random()`、`crypto.getRandomValues()`、`crypto.randomBytes()`、`Date.now()` 出現在 `rules-engine`；亂數只能透過 `ctx.rng(流名稱)` 取得（技術規劃 §12-5）。
2. 禁止只把房間權威狀態存在記憶體。
3. 禁止在 WebSocket handler 寫卡牌規則。
4. 禁止 `any`（TS）、未標型別的 GDScript 公開函式與網路 DTO。
5. 禁止關閉、跳過、刪除既有測試或 lint 規則來讓 CI 通過。
6. 禁止未經 ADR 新增執行期依賴套件（開發工具類在 PR 說明理由即可）。
7. 禁止修改 `docs/design/` 任何文件，除非任務明確要求。
8. 禁止把 Token、密碼、`.env` 寫進程式碼、日誌、測試快照或 commit。
9. 禁止 Godot 3 語法（`onready`、`yield`、`Tween` 當節點、舊 `WebSocketClient`）；只用 Godot 4 API。
10. 禁止為了「看起來完成」留下假實作；做不到的部分要明確寫進 PR 的「未完成」欄。
11. 禁止一次 PR 超過 **400 行**手寫變更（不含產生檔、YAML 內容、測試資料）；超過就拆。

## 5. 工作流程（每個任務都照做）

1. **讀**：本檔＋目前階段文件＋任務提到的設計文件段落。
2. **計畫**：先輸出計畫（要改哪些檔、為什麼、怎麼測），等人類確認後才寫程式。小於 50 行的修正可以直接做。
3. **測試先行**：規則、協定、資料庫的變更，先寫失敗的測試，再實作。
4. **實作**：一次只做一個需求 ID（例如 `M1-R03`）。
5. **自我檢查**：跑 `pnpm typecheck && pnpm lint && pnpm test`（Godot 變更另跑 GUT），全部通過才交付。
6. **交付**：照 `.github/pull_request_template.md` 填寫，含需求 ID、測試結果、未完成項目、需要人類決定的問題。
7. **審查**：由**另一個 AI 工具**依 `docs/review/` 審查，再由人類合併（見 `docs/review/審查流程.md`；分支、提交訊息、CI 見 `docs/review/CI與分支規則.md`）。

## 6. 程式風格

### TypeScript（server、rules-engine、protocol、mobile-web、admin-web、tools）

- `strict: true`、`noUncheckedIndexedAccess: true`、`exactOptionalPropertyTypes: true`。
- 外部輸入（WebSocket、HTTP、YAML、資料庫讀出）一律先 Zod parse，再轉成內部型別；禁止 `as` 強轉未驗證資料。
- 規則引擎：狀態不可變（回傳新物件）；Reducer 簽名 `(state, command, ctx) => { state, events }`，`ctx` 帶 `rng`、`now`。
- 錯誤用回傳的 Result／拒絕代碼表示規則錯誤；`throw` 只用在程式錯誤。
- 檔名 `kebab-case.ts`；型別 `PascalCase`；函式與變數 `camelCase`；常數 `UPPER_SNAKE_CASE`。

### GDScript（godot-client）

- 公開函式、成員變數、訊號參數全部標型別；網路資料一律用產生的 DTO 類別。
- Autoload 只放：`Net`（WebSocket）、`Store`（Projection）、`Clock`（時鐘校正）、`Presenter`（演出佇列）、`I18n`。
- 場景負責呈現；不在場景腳本裡解讀規則。
- Scene 自給自足（不用 `../..` 存取外部節點，依賴由父層注入）、Resource 不存執行中數值、`await` 之後重新檢查節點：完整清單見 `docs/checklists/02_Godot專用檢查表.md`。
- 檔名 `snake_case.gd`；類別 `PascalCase`（`class_name`）。

### 共通

- 函式超過 60 行、檔案超過 400 行就要拆。
- 註解寫「為什麼」，不寫「做什麼」；引用設計文件時寫章節，例如 `// 規則優先序 §6 傷害公式`。
- 顯示文字一律走語系鍵（`i18n/zh-TW.json`），不寫死在程式。

## 7. 專案結構

見 `docs/design/命運酒館_技術規劃.md` 第 10 節。新增頂層資料夾要先開 ADR。

## 8. 常用指令


# 審查流程：AI 交叉審查＋人工合併

## 1. 原則

- **寫程式的 AI ≠ 審查的 AI**：同一個工具（甚至同一個模型的另一個對話）不能審查自己寫的程式。
- **AI 審查是過濾，人類核准才合併**：AI 找問題，人類做決定。
- **審查依清單**：每次審查都要跑通用清單＋該變更領域的專用清單，不靠臨場發揮。

## 2. 工具分工

| 實作者 | 第一審查者 | 第二審查者（🔴 才需要） |
|---|---|---|
| Claude Code（Claude Pro） | Gemini（Google AI Plus）新對話：一般審查（審查提示詞 §1） | Gemini **另一個**新對話：規則與安全專審（審查提示詞 §5），看不到第一份報告 |

- 2026-11-25 依實際工具調整：實作只用 Claude、審查只用 Gemini（見 `docs/prompts/AI工具與上下文.md`）。

- 每個 PR 在說明欄記錄「實作工具」與「審查工具」。

## 3. 風險分級

| 等級 | 什麼樣的變更 | 需要的審查 |
|---|---|---|
| 🔴 高 | `rules-engine`、`protocol`、`database` migration、事件儲存與快照、權限與 Token、覆寫、可見性過濾 | **兩份 Gemini 審查**（兩個不同的新對話：一般＋規則與安全，第二個看不到第一份報告）＋你核准；核准前隔天再看一次 diff |
| 🟡 中 | `server` 其他部分、`content` YAML、小遊戲計分、Godot 的 `Net`／`Store`／`Presenter` | 一個 AI 審查＋你核准 |
| 🟢 低 | UI 版面、美術、文字、文件、測試補強 | 一個 AI 審查＋你核准；小黃的 Godot 場景與美術 PR 由你核准，你的演出框架改動影響場景時請小黃看一次 |

- 🔴 路徑寫在 `.github/risk-paths.yml`；合併前由 `review-gate` 檢查審查是否齊全（GitHub Free 私有 repo 沒有分支保護，靠自律＋事後稽核，見 `docs/review/CI與分支規則.md`）。
- **2026-11-25 兩人團隊**：程式全部由你寫，沒有第二位工程師，所以「非作者核准」改由**不同廠商的 AI 獨立審查**（實作 Claude、審查 Gemini）補上；你是作者也是核准者，因此 🔴 變更一律等 CI 全綠＋兩份審查報告的每條意見都已處理才合併，不能跳過。

## 4. 流程

```
1. 開 Issue（需求 ID、範圍、驗收條件）
2. 實作 AI：計畫 → 人類確認 → 測試先行 → 實作 → 自我檢查（typecheck／lint／test）
3. 開 PR（照 PR 模板；附測試結果、未完成、需要決定的事）
4. CI 全綠（不綠不審）
5. 審查 AI：依「審查提示詞」＋清單輸出審查報告，貼在 PR 留言
6. 作者處理：每條意見標記「已修正／不同意（附理由）／開新 Issue」
7. 🔴 變更：第二個審查 AI 重跑
8. 人類核准 → Squash merge
```

## 5. 審查報告格式

```
## 審查報告
- 實作工具：Claude Code｜審查工具：Gemini（Google AI Plus）｜審查重點：一般
- 範圍：M3-R08 傷害管線（PR #42）
- 結論：需要修改／可以合併

| # | 嚴重度 | 檔案:行 | 問題 | 依據（文件章節或清單項目） | 建議 |
|---|---|---|---|---|---|
| 1 | 🔴 阻擋 | damage.ts:88 | 上限寫死 30 | 清單 R-07；規則優先序 §6 | 改讀設定 |

### 架構邊界檢查（AGENTS.md §3）：通過／不通過（列出違反項）
### 硬性禁止檢查（AGENTS.md §4）：通過／不通過
### 測試是否足夠：…
### 文件矛盾或需要企劃決定的事：…
```

| 嚴重度 | 定義 | 處理 |
|---|---|---|
| 🔴 阻擋 | 違反架構邊界、硬性禁止、規則錯誤、安全問題、資料遺失風險 | 必須修正才能合併 |
| 🟡 重要 | 缺測試、可讀性差、效能隱憂、設計文件沒寫清楚 | 修正，或開 Issue 並在 PR 說明 |
| 🟢 建議 | 命名、風格、可選的改善 | 作者決定 |

## 6. 人類核准者的最後檢查（5 分鐘）

- [ ] CI 全綠；沒有被跳過的測試。
- [ ] 審查報告的 🔴 全部處理。
- [ ] PR 改動符合 Issue 範圍，沒有夾帶其他修改。
- [ ] 規則類變更：隨機挑一個測試，對照設計文件確認預期值是對的（AI 可能寫錯測試又寫錯實作，兩者一致但都錯）。
- [ ] 沒有新的執行期依賴（或已有 ADR）。

## 7. 防止 AI 審查失效的做法

- 審查 AI **只拿到**：AGENTS.md、相關設計文件章節、清單、PR diff、測試結果；**不拿實作的對話紀錄**（避免被實作者的推理帶著走）。
- 要求審查 AI 對每一條「通過」也寫出檢查依據（例如「已確認 damage.ts 第 40～60 行沒有讀取時間」），避免空泛的「看起來沒問題」。
- 每週抽一個已合併的 PR，人工重審一次，記錄 AI 漏掉的問題，回饋到清單。

# 審查清單

> 每次審查：**通用清單（G）**＋變更涉及的領域清單。審查報告引用項目編號（例如 `R-07`）。

## G｜通用（每個 PR）

| # | 檢查項目 |
|---|---|
| G-01 | PR 有需求 ID，改動範圍符合 Issue，沒有夾帶無關修改 |
| G-02 | 手寫變更 ≤ 400 行（不含產生檔、YAML 內容、測試資料） |
| G-03 | CI 全綠；沒有 `skip`、`only`、被註解掉的測試；沒有放寬 lint 規則 |
| G-04 | 沒有違反 AGENTS.md §3 架構邊界 |
| G-05 | 沒有違反 AGENTS.md §4 硬性禁止 |
| G-06 | 沒有新增未經 ADR 的執行期依賴 |
| G-07 | 沒有 Token、密碼、`.env` 內容出現在程式碼、日誌、測試快照 |
| G-08 | 顯示文字都走語系鍵 |
| G-09 | 函式 ≤ 60 行、檔案 ≤ 400 行；命名符合規範 |
| G-10 | 註解說明「為什麼」，規則相關程式有引用設計文件章節 |
| G-11 | 沒有假實作、沒有留下無 Issue 編號的 TODO |
| G-12 | 文件矛盾或企劃未定的地方，已用【需要決定】格式提出，而不是自行決定 |

## R｜規則引擎（`packages/rules-engine`、`content`）

| # | 檢查項目 |
|---|---|
| R-01 | 純函式：沒有 I/O、沒有 `Math.random`、`crypto.getRandomValues`、`Date.now`、`new Date(`；亂數只用 `ctx.rng(流名稱)`，整數用拒絕取樣、洗牌用 Fisher–Yates、機率用整數；時間與亂數只來自 `ctx` |
| R-02 | 狀態不可變；沒有修改傳入的 `state` |
| R-03 | 結算順序符合《規則優先序》§2、§3 與《技術規劃》4-7 |

# 命運酒館｜CI 與分支規則 v1.1

> 更新日期：2026-11-25（v1.1：🔴 的兩份審查改成兩個不同重點的 Gemini 對話；v1.0：定案，確認紀錄見第 7 節）
> 用途：GitHub Actions 每個流程跑什麼、多久要跑完；你一個人開發時的分支、提交、合併規則。AI 建立 `.github/workflows/` 時照本文件。
> 依據：《審查流程》§3、§4、《審查清單》、《技術限制》、《工作清單》§1、各階段驗收條件。

---

## 1. 分支與合併

| 項目 | 規則 |
|---|---|
| 模式 | 主幹開發：只有 `main` 一條長期分支；每個任務一條短分支，做完就合併刪掉 |
| 分支名稱 | `t/T-M0-07-protocol-envelope`（任務 ID＋簡短英文） |
| 一個任務 | 一條分支、一個 PR；同時最多 2 個進行中（工作清單 §1） |
| 合併方式 | 只允許 **Squash merge**；合併後自動刪分支 |
| 直接推 `main` | 禁止。GitHub Free 的私有 repo 沒有分支保護（Q5），**這條靠自律**；`main.yml` 會偵測沒經過 PR 的推送並開 Issue（第 1-2 節） |
| `main` 壞掉 | 先 revert 造成問題的 PR，再開新分支修；不在 `main` 上直接修 |
| 提交訊息 | 英文、Conventional Commits：`feat(rules-engine): add damage pipeline [T-M3-07]`；PR 標題同格式，squash 後成為 `main` 上的那一筆 |
| PR 內文 | 照 `.github/pull_request_template.md`：任務 ID、需求 ID、`Closes #<Issue>`、實作工具、審查工具、測試結果、未完成、需要決定的事、人類最後檢查勾選 |

### 1-1 一個人時怎麼「核准」（Q1）

GitHub 不能讓 PR 作者核准自己的 PR；而且 GitHub Free 的私有 repo 沒有分支保護，CI 擋不住合併。所以改用一個 CI 檢查 `review-gate` 亮燈，**你只在 `review-gate` 和 `pr.yml` 全綠時才按合併**：

| `review-gate` 檢查 | 條件 |
|---|---|
| 審查報告 | PR 留言中有 `## 審查報告`，且「審查工具」和 PR 內文的「實作工具」不同（實作 Claude、審查 Gemini） |
| 🔴 變更 | 改到 🔴 路徑（審查流程 §3：`rules-engine`、`protocol`、`database`、事件儲存、權限與 Token、覆寫、可見性過濾）時，要有**兩份**審查報告：「審查重點」一份是「一般」、一份是「規則與安全」（都是 Gemini，不同對話；AI 工具與上下文 §2-1） |
| 意見處理 | 審查報告的每條 🔴 意見都有回覆標記（已修正／不同意＋理由／開新 Issue） |
| 人類最後檢查 | PR 內文「人類最後檢查」5 項全部打勾（審查流程 §6） |
| 🔴 冷卻 | 🔴 PR 從最後一次推送到合併至少隔 **12 小時**（「隔天再看一次 diff」） |

- `review-gate` 在 PR 留言或內文變動時重跑（`issue_comment`、`pull_request` 的 `edited` 事件）。
- 路徑對應的風險等級寫在 `.github/risk-paths.yml`，`review-gate` 與 Issue 範本共用。
- `CODEOWNERS` 在 Free 方案的私有 repo 不會生效，保留只當「哪些路徑是 🔴」的說明。

### 1-2 事後稽核（補上沒有分支保護的缺口）

| 檢查 | 做法 |
|---|---|
| 合併時 `review-gate` 或 `pr.yml` 不是綠燈 | `main.yml` 在每次合併後查這個 PR 的檢查結果；不是全綠就自動開 Issue（標籤 `gate-bypass`），附 PR 連結 |
| 沒經過 PR 直接推到 `main` | `main.yml` 檢查這筆提交有沒有對應的 PR；沒有就開 Issue（標籤 `gate-bypass`） |
| 處理 | `gate-bypass` Issue 要在下一個任務開始前補上審查（補跑審查 AI、補報告），或 revert |
| 每週 | 每週檢查一次看板，`gate-bypass` 必須是 0 |

# 技術限制

> AGENTS.md §3、§4 是硬性規則；本檔補充可量測的預算與上限。數值有 ⚠️ 的，灰盒測試後可以調整，但要開 ADR。

## 1. 效能預算

| 項目 | 上限 | 量測方式 |
|---|---|---|
| 伺服器處理一個命令（含資料庫交易） | p95 < 50 ms（本機）、< 150 ms（雲端） | Pino 欄位 `durationMs` |
| Node.js Event Loop 延遲 | p95 < 50 ms | `monitorEventLoopDelay` |
| 規則引擎單次 `reduce`（不含 I/O） | < 5 ms | 基準測試 |
| 快照大小 | < 1 MB | 資料庫監控 |
| 單一 WebSocket 訊息 | ≤ 64 KB | 協定驗證 |
| 手機首次載入（壓縮後 JS） | < 500 KB ⚠️ | Vite build 報告 |
| 手機小遊戲幀率 | ≥ 50 fps（中階手機） | 實機量測 |
| Godot 主螢幕 | ≥ 60 fps（1080p）；單一工作每幀 < 2～3 ms | Godot Profiler |
| 拔河狀態延遲（手機 → 主螢幕） | < 300 ms | 遙測 |

## 2. 時間限制

| 項目 | 數值 | 來源 |
|---|---|---|
| 一般選擇時限 | 20 秒 | 技術規劃 T2 |
| 反應窗時限 | 每層 5 秒；全員回應即關閉 | 技術規劃 T2 |
| 小遊戲 | 準備 3 秒＋對決約 10 秒（總計 ≤ 15 秒）；平手加賽每次 ≤ 5 秒 | 設定總表 §7；小遊戲規格 |
| 演出保底 | `maxDurationMs + 3000` | 訊息格式 §10 |
| 心跳／逾時 | 5 秒／15 秒（主螢幕 10 秒，逾時即暫停對局） | 訊息格式 §5；技術規劃 §12-3 |
| 斷線座位保留 | 3 分鐘 | 技術規劃 §4-4 |
| 單局目標 | 4 人局約 2.5 小時 | 設定總表 §1 |
| 演出時長預算 | 系統演出平均每次行動 ≤ 20 秒；各演出上限見決策流程 §4 | 技術規劃 T9 |

## 3. 程式規模

| 項目 | 上限 |
|---|---|
| 單一 PR 手寫變更 | 400 行（不含產生檔、YAML 內容、測試資料） |
| 函式 | 60 行 |
| 檔案 | 400 行 |
| scripted handler | 每個都要有測試；MVP 期間總數 ⚠️ 不超過 15 個（超過代表效果元件設計不足，需要檢討） |

## 4. 依賴管理

- 執行期依賴要開 ADR（理由、替代方案、授權、維護狀況）。
- 開發依賴在 PR 說明理由即可。
- 授權只接受：MIT、Apache-2.0、BSD、ISC、PostgreSQL License、MPL-2.0（MPL 需註記）；GPL 類不接受。
- `pnpm-lock.yaml` 必須提交；CI 用 `--frozen-lockfile`。

## 5. 安全

- Token：高熵（≥ 128 bit）、只存雜湊、不放網址參數（QR 內的一次性 Join Token 除外）。
- 速率限制：加入 API、短碼嘗試、WebSocket 訊息頻率（⚠️ 每連線每秒 30 則）。
- 管理後台與玩家 API 分開路由與認證。
- 日誌、錯誤追蹤一律遮罩 Token；不記錄玩家輸入內容全文。

## 6. 資料

- 事件只增不改；修正用補償事件。
- 每日備份；每個里程碑至少做一次還原演練。
- 遙測只用匿名 ID 與暱稱，不收集其他個人資料。

# ADR-0001～0006：初始技術決策（彙整）

- 狀態：已採用
- 日期：2026-11-23
- 詳細比較與切換條件見《命運酒館_技術規劃》第 2、9 節。

| 編號 | 決定 | 主要理由 | 重新檢討的條件 |
|---|---|---|---|
| ADR-0001 | 主螢幕用 **Godot 4 穩定版＋靜態型別 GDScript**；不用 C#；C++ GDExtension 只作效能預留 | 免費（MIT）、2D／2.5D 與 UI 整合最好、灰盒迭代快；規則在伺服器，不需要 C# 強化客戶端 | Godot 無法支援必要的 Steam／輸入／SDK；或 Profiler 證明效能瓶頸 |
| ADR-0002 | 伺服器用 **Node.js＋Fastify＋標準 WebSocket（ws）**；不用 Colyseus、Socket.IO | 三端都原生支援標準 WebSocket；協定完全自控；規則與前端共用 TypeScript | 自建斷線恢復與房間管理成本過高（改 Socket.IO）；Event Loop p95 持續超過 50～100 ms |
| ADR-0003 | **伺服器權威＋事件儲存＋快照**（PostgreSQL） | 2.5 小時長局必須能從崩潰恢復、可重播、可審計、可回滾 | 無（核心原則） |
| ADR-0004 | 卡牌內容用 **YAML＋受控效果元件**，特殊效果只能用有測試的 TS handler | 企劃改數值不用改程式；避免演變成不安全的腳本語言 | 非工程人員大量編輯、YAML 錯誤影響效率（改內容編輯器） |
| ADR-0005 | 協定 **Zod 單一來源** → JSON Schema → TS 型別＋GDScript 類別 | 三端不會各寫一份而漂移；契約測試自動化 | 頻寬或序列化成為瓶頸（改 MessagePack／Protobuf） |
| ADR-0006 | 手機與後台用 **React＋Vite＋TypeScript**；手機先網頁，之後可包 App | 免安裝、掃碼即玩；與伺服器共用型別 | 低階手機效能或載入大小成為實測問題（改 Preact／Svelte） |
