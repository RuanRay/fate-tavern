# 00｜階段總覽與共通完成定義

> 依《命運酒館_技術規劃》第 12 節的 M0～M8。每個階段一份文件：`M0_骨架與合約.md` … `M8_房主工具與灰盒版.md`。


# M0｜骨架與合約

> **2026-11-25 階段調整**：第一階段只有文字版主螢幕（`tools/fake-host`），所以 M0 **不做 Godot**。R10、R14 的 GUT 端、A02 的 Godot 部分、A08 的 GUT 端、§分工表 C 列的 Godot 專案設定，全部移到**第二階段 Godot 框架**（技術規劃 §12-1）。M0 改為：TS 端契約測試＋文字版主螢幕顯示房間碼與 QR。R19 測試硬體改為：你的筆電＋iPhone 13（見版本鎖定）。

## 1. 目標與範圍

**目標**：建立 monorepo 與 CI，讓主螢幕（Godot）、手機、後台三端都能透過正式協定連上同一個房間；協定的「單一來源 → 產生三端型別 → 契約測試」流程從第一天就跑起來。

| 範圍內 | 範圍外 |
|---|---|
| monorepo、套件管理、TS 設定、lint、格式化 | 任何遊戲規則 |
| Docker Compose（PostgreSQL） | 事件儲存（M1） |
| Fastify 伺服器：健康檢查、開房、加入、WebSocket 握手、心跳 | 命令管線（M1） |
| `packages/protocol`：信封、`session.*`、`error.*` | 其他訊息類別 |
| `tools/protocol-codegen`：Zod → JSON Schema → GDScript | — |
| Godot：連線、顯示房間碼與 QR、玩家列表 | 地圖、演出 |
| 手機：掃碼加入、輸入暱稱、顯示「已連線」 | 遊戲操作 |
| 後台：登入頁與房間列表（唯讀） | 覆寫、回滾（M8） |
| GitHub Actions、PR 模板、CODEOWNERS | — |

## 2. 前置條件

- 鎖定版本（見 `docs/constraints/版本鎖定.md`）：Node.js LTS、pnpm、TypeScript、Godot 4 穩定版、PostgreSQL。

## 4. 技術細節

### 4-1 資料表（M0）

```
rooms(id text pk, code text unique, status text, created_at timestamptz, host_session_hash text)
room_members(room_id text fk, player_id text, role text, nickname text, seat int, joined_at timestamptz, removed_at timestamptz null)
sessions(token_hash text pk, room_id text, player_id text, role text, expires_at timestamptz, revoked_at timestamptz null)
```

- Token 只存 SHA-256 雜湊。
- ID 前綴照《訊息格式》第 15 節（`rm_`、`pl_`、`st_`）。

### 4-2 伺服器模組

```
apps/server/src/
├─ app.ts                Fastify 建立、外掛註冊
├─ config.ts             環境變數（Zod 驗證）
├─ transport/http/*.ts   路由
├─ transport/ws/*.ts     連線、握手、心跳、信封解析、序號
├─ rooms/room-registry.ts 房間與連線對應（M0 只存連線，不存遊戲狀態）
├─ auth/tokens.ts        產生、雜湊、驗證、撤銷
└─ observability/log.ts  Pino（Token 遮罩）
```

### 4-3 序號

- 每條連線各自維護 `seq`（伺服器送出端從 1 遞增）；M0 先實作遞增與 `ackSeq` 欄位，補發緩衝在 M1 實作。

### 4-4 GDScript 產生物範例（產生器輸出的樣子）

```gdscript
class_name SessionWelcome
extends RefCounted

var player_id: String
var role: String
var server_time: int
var heartbeat_interval_ms: int
var heartbeat_timeout_ms: int
var content_version: String
var state_version: int

static func from_dict(d: Dictionary) -> SessionWelcome:
	var o := SessionWelcome.new()
	o.player_id = d.get("playerId", "")
	# …由產生器輸出，禁止手改
	return o
```

- 產生檔頂端加註 `# 自動產生，請勿手動修改`，CI 檢查一致性。

### 4-1 資料表（新增；完整欄位以《命運酒館_資料庫結構》v1.0 §2-2 為準，含 `match_players`）

```
matches(id pk, room_id fk, seed bytea /* 32 bytes，只有伺服器與 admin 可讀 */, seed_commitment text, content_version text, rules_version text, status text, started_at, ended_at)
events(match_id fk, state_version int, event_id text unique, event_type text, event_version int,
       visibility text, owner_id text null, viewer_ids text[] null, data jsonb, causation_id text,
       state_hash text, occurred_at timestamptz, primary key(match_id, state_version))

outbox(id bigserial pk, match_id fk, kind text, payload jsonb, created_at, processed_at null)
```

- `events.state_hash`：該事件套用後的狀態雜湊（用於恢復驗證與除錯）。
- 系統命令（逾時等）也寫入 `commands`，`player_id = 'system'`。

### 4-2 管線虛擬碼

```ts
async function handleCommand(room: Room, env: Envelope): Promise<void> {
  const cached = await commands.find(env.messageId);
  if (cached) return reply(cached.result);                    // 冪等
  const cmd = parseCommand(env);                               // Zod
  authorize(room, env.sender, cmd);                            // 身分、角色
  const ctx = { rng: room.rng(), now: clock.now() };
  const out = reduce(room.state, cmd, ctx);                    // 純函式
  if ('rejected' in out) return saveAndReply(env, out);        // 拒絕也存（冪等）
  await db.transaction(async tx => {
    await tx.events.append(out.events);
    await tx.commands.save(env, { accepted: true, ... });
    if (shouldSnapshot(out)) await tx.snapshots.save(out.state);
  });
  room.state = out.state;                                      // 寫入成功後才更新記憶體
  reply(accepted); broadcastFiltered(out.events); emitPresentation(out.events);
}
```

### 4-3 狀態雜湊

- 正規化：物件鍵排序、陣列保留順序、數字一律整數、不含 `undefined`。
- 公開雜湊（給主螢幕校驗）與完整雜湊（伺服器內部）分開計算。

### 4-4 時間

- 伺服器 `clock.now()` 只在管線入口取一次，放進 `ctx.now` 與事件的 `occurredAt`；Reducer 只能用 `ctx.now`。
- 重播時 `ctx.now` 取自事件紀錄，不用真實時間。

## 4. 技術細節

### 4-1 狀態（節錄；完整定義以《命運酒館_遊戲狀態模型》v1.0 為準，本節只是舊示意）

```ts
interface GameState {
  phase: TurnPhase;           // 'turn_start' | 'pre_roll' | ...
  round: number; week: number; targetWeeks: number;
  turnOrder: PlayerId[]; currentIndex: number;
  map: MapDef;
  players: Record<PlayerId, PlayerState>;
  zodiac: { current: ZodiacId | null; turnsInCurrent: number; drawnThisCycle: ZodiacId[] };
  pendingPrompt: Prompt | null;
  rng: RngState;
}
interface PlayerState {
  position: number; laps: number; hp: number; hpMax: number; gold: number; clarity: number;
  statuses: Status[]; alive: boolean;
}
```

### 4-2 周數計算

- 已定案（2026-11-24）：`week = max(1, min(laps of alive players))`。開局到最少圈數達 1 之前都是第 1 周，所以第 1 周約是其他周的兩倍長。
- 時間上限：最少圈數達到 `targetLaps`（4 人局 4）時觸發 `game.time_limit_reached`（約 37 回合）。
- 死亡玩家不參與最小值計算（死亡在 M7；M2 先保留欄位）。

### 4-3 星座切換條件

```
切換時機 = 周數增加時，或 turnsInCurrent ≥ X（4 人局 X = 11）
抽取：從本輪未抽過的星座中以種子亂數挑一個；12 個抽完才重置
```

### 4-4 Godot 地圖排列

- 正 n 邊形（4 人局 n＝7），每邊格數＝28 ÷ 7＝4；地標格（`landmarks`）放在頂點。
- 只依格子順序計算座標，**不在場景編輯器手擺格子**。
- 斜俯視：地圖節點做 2D 投影（Y 軸壓縮＋前後排序），不用 3D 相機。

## 7. 測試要求

- 單元：周數、起點收入、後退、清醒反噬的每個邊界（3%、2%、0%）。
- 性質測試：任何命令序列後 `0 ≤ clarity ≤ 100`、`gold ≥ 0`、`0 ≤ position < 28`。
- 重播：加入 M2 的黃金劇本 10 組。
- GUT：七邊形座標、地標位置、骰面重新對應。

## 8. 審查重點

- 規則數值是否寫在設定檔或內容檔，而不是散落在程式碼。
- 狀態機每個階段是否都可被暫停／恢復（重啟後能從任一階段繼續）。
- Godot 是否有任何根據規則自行推算的邏輯（例如自己算起點收入）。

## 9. 限制與禁止

- 不准把地圖排列寫死；排列一律由對局種子產生。
- 數值（30、−3、71／51、X＝11）必須來自 `content/config/*.yaml`，不准寫死。
- Godot 的地圖不准手擺。

## 4. 技術細節

### 4-1 效果元件定義（範例）

```ts
const Damage = defineEffect('damage', z.object({
  target: TargetSelector,
  amount: z.number().int().nonnegative(),
  kind: z.enum(['attack', 'dot', 'environment']).default('attack'),
}), (ctx, p) => pipeline.damage(ctx, resolveTargets(ctx, p.target), p.amount, p.kind));
```

### 4-2 YAML 範例（寶劍十正位，含醉意版本）

```yaml
- id: minor.swords.10
  kind: minor_card
  orientation: upright
  effects:
    - { type: damage, target: self, amount: 10, kind: environment }
    - { type: drink, target: others, cups: 1 }
    - { type: on_death_from_this, soul_fire_threshold_delta: -2 }
  tiers:
    sober:
      extra:
        - { type: transfer_gold, from: others, to: self, amount: 5 }
    drunk:
      override:
        - { type: damage, target: self, amount: 12, kind: environment }
        - { type: drink, target: others, cups: 1 }
        - { type: on_death_from_this, soul_fire_threshold_delta: -4 }
```

### 4-3 結算堆疊

- 堆疊、反應鏈、觸發佇列的欄位照《命運酒館_遊戲狀態模型》§12。
- 用顯式堆疊（不用遞迴）表示「事件 → 子效果 → 觸發」，以便在任何輸入請求處暫停、序列化、重啟後繼續。
- 每個效果實例有唯一 ID；同一事件內每個替代效果最多套用一次。

### 4-4 傷害計算明細

- `damage.applied` 事件要帶計算明細：`base`、`replacedBy`、`percentTotal`、`flat`、`reduction`、`beforeCap`、`final`、`capped`、`immuneReason`。

## 4. 技術細節

### 4-1 手機端結構

```
apps/mobile-web/src/minigames/
├─ framework/        共用：倒數、計時（伺服器時間換算）、輸入紀錄、上傳
├─ tug-of-war/  quick-draw/  rune-spotting/  drink-order/  forging/
├─ stopwatch/   rune-rps/    chicken/        coin-count/
└─ registry.ts       gameId → 元件
```

- 每個小遊戲是獨立模組，介面：`mount(container, prepare, clock, send) → unmount`。
- 題目由 `seed` 產生，產生函式放在 `packages/protocol` 共用（伺服器重播與驗證也用同一份）。

### 4-2 公平性

- 反應類比的是「本地時間差」：從手機畫面真正顯示訊號的那一幀（`requestAnimationFrame` 時間）到觸控事件時間。
- 伺服器用延遲模擬測試（100～300 ms 抖動）確認結果不受網路影響。

- 覆寫是否只新增事件、必填理由。
- 後台是否有任何玩家可以觸及的入口。
