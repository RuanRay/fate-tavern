# 01｜專案檢查表（命運酒館版）

## 3. 核心概念（G1）

**一句話**：玩家是命運酒館裡的冒險者，透過擲骰移動、抽塔羅與盧恩牌觸發事件、用手機小遊戲決鬥、喝酒換取風險與報酬，達成「拍下聖物繞完一圈」或「最後存活」。本作的特色是**電視＋手機的非對稱派對體驗，加上醉意本身就是遊戲數值**。

| 項目 | 內容 |
|---|---|
| 玩家扮演 | 6 種職業之一（聖殿騎士、魔法師、遊俠、商人、賭徒、祭司） |
| 反覆進行的行動 | 擲骰 → 移動 → 觸發格子事件（抽牌、決鬥、購物、拍賣、賭場、祭壇）→ 選擇與互動 |
| 最有特色的地方 | 清醒值＝醉意：越醉越容易抽到逆位（爆發或倒楣）；喝酒是代價、懲罰也是資源 |
| 主要輸入方式 | 手機觸控（直式、單手、大按鈕） |
| 單機／多人 | 同一個客廳的多人（每人一支手機）；伺服器在雲端，架構預留異地遊玩 |

**參考遊戲**（2026-11-25 確認）

| 參考遊戲 | 參考項目 | 本作差異 |
|---|---|---|
| Mario Party | 棋盤移動＋小遊戲 | 小遊戲只用在攻防、約 15 秒；有正式的經濟與勝利路線；成人向、喝酒系統 |
| Jackbox Party Pack | 電視＋手機的派對形式 | 本作是一局 2.5 小時的完整策略遊戲，不是短局問答 |
| 桃太郎電鐵 | 一局很長的棋盤遊戲；追趕機制；黏著落後者的負面角色（窮神） | 用來對照「長局是否撐得住」與死神追逐的壓力設計；本作有直接對打與喝酒 |
| Dokapon Kingdom | 棋盤上直接對打、互相陷害、一局數小時 | 最接近本作「競技＋惡意互動」的參考；本作沒有 RPG 成長、改用醉意與塔羅 |

- 原本列的大富翁／いただきストリート移除：本作沒有地產，相似處只剩繞圈。

**核心循環檢查**

- [x] 每輪都有風險與收益（喝酒換報酬、逆位爆發）
- [x] 至少兩種可行策略（經濟勝利／血量勝利；6 職業偏向不同）
- [ ] 玩家是否「知道現在要做什麼」：由 M2 灰盒試玩驗證
- [ ] 2.5 小時是否值得：⚠️ M2 灰盒試玩只有部分機制，完整時長要到 M8 灰盒版才能驗證（2026-11-25 取消紙本試玩後的已知風險）

**灰盒原型試玩**

- 時間點：M2 結束（約 2027-02 初），用文字版假主螢幕＋手機＋規則核心，只有擲骰、移動、酒館小牌、清醒值。
- 至少 5 位沒參與開發的人；不逐步解說；記錄：第一次卡住的地方、誤解的規則、每個人覺得最有趣與最無聊的格子。
- 三人以上在同一處卡住就優先修改；不要只問「好不好玩」。
- 試玩紀錄模板：測試日期、版本、人數、第一次卡住位置、最常見誤解、最受歡迎、最無趣、下一步修改。

# 02｜Godot 專用檢查表（命運酒館版）

> 來源：使用者提供的「Godot 專用問題與檢查表」（2026-11-24），依本專案改寫。
> 本專案的 Godot **只做呈現**（AGENTS §3 B1）：不判定規則、不做物理碰撞判定、不存檔。所以原表的 Hitbox／Hurtbox、Collision Layer、角色物理移動、存檔等項目不適用；保留的是 Scene 結構、Autoload、Signal、Resource、生命週期、await、UI、型別、效能這些和呈現層直接相關的部分。
> 審查時對應 `docs/review/審查清單.md` 的 GD 區；本檔是 GD 區的展開版。

---

## 1. Scene 自給自足、依賴由上層注入

- [ ] 可重用 Scene（格子、玩家棋子、玩家面板、卡牌、骰子）不使用 `../..` 存取外部節點
- [ ] 外部依賴由父層呼叫 `initialize(...)` 注入；子 Scene 用 Signal 回報事件
- [ ] 每個 Scene 可以單獨按 F6 執行（用假資料）
- [ ] 不以 `get_parent().get_parent()`、`find_child()` 作為主要架構
- [ ] 不在 `_process()` 中反覆 `get_node()`

## 2. NodePath

- [ ] 跨 Scene 依賴用 `@export` 型別欄位在 Inspector 指定，不寫深層路徑
- [ ] 重要節點引用有型別（例如 `@onready var panel: PlayerPanel = $Panel`）
- [ ] 不用節點名稱判斷遊戲邏輯（反正 Godot 也不該有遊戲邏輯）

## 3. Autoload

本專案固定 5 個（AGENTS §6）：`Net`、`Store`、`Clock`、`Presenter`、`I18n`。

- [ ] 沒有第 6 個 Autoload（新增要開 ADR）
- [ ] 沒有全能型 GameManager；Autoload 不持有某個場景節點的永久引用
- [ ] 回到大廳、重新開房時，`Store`、`Presenter` 會完整重設
- [ ] `Store` 只存伺服器給的投影（Projection），不存自己算出來的遊戲數值

## 4. Signal

- [ ] Signal 名稱用過去式（`dice_landed`、`presentation_finished`）、參數有型別
- [ ] 父控制子用直接呼叫；子通知父用 Signal；跨整個遊戲的事件才走 Autoload
- [ ] 重新進入場景不會重複連接（必要時 `is_connected()`）
- [ ] 沒有 A 通知 B、B 又立刻通知 A 的循環

## 5. Resource 共用

- [ ] Resource 只保存靜態呈現設定（格子外觀、職業立繪、卡面、演出時長）
- [ ] 執行中的數值（某玩家的生命、金幣）**不寫進** Resource；它們只存在 `Store`
- [ ] 若真的需要每個實例獨立的 Resource，用 `duplicate(true)`，並確認巢狀 Resource
- [ ] 遊戲執行中不會改寫任何 `.tres`

## 6. 不是所有東西都要做成 Node

- [ ] 純資料轉換（DTO → 顯示用資料、格子座標計算）用 `RefCounted` 或靜態函式
- [ ] 這些轉換可以在 GUT 中不載入 Scene 直接測試

## 7. `_process()`、Tween 與演出

（本專案沒有物理角色移動；棋子移動、翻牌、數值變化都是演出。）

- [ ] 演出用 Tween、AnimationPlayer，或 `_process(delta)` 乘以 delta，不用固定位移
- [ ] 同一個 Transform 不會同時被兩個 Tween 或 `_process` 修改
- [ ] 演出速度設定（1x／1.5x／2x）只改播放速度，不改伺服器結果
- [ ] 已在 30、60、144 FPS 下測試演出時長與完成回報一致

## 8. `queue_free()` 與已刪除物件

- [ ] `queue_free()` 之後不再對該節點執行流程
- [ ] 延遲回呼、Timer timeout 前用 `is_instance_valid()` 確認
- [ ] 同一個演出的「完成回報」只送一次

## 9. `await` 之後環境可能已經變了

- [ ] 每個 `await` 之後重新確認節點與 `Store` 狀態仍然有效
- [ ] 收到新快照（重連、回滾）時，正在播放的演出能被取消並清理
- [ ] 連點按鈕不會啟動多份相同流程
- [ ] 演出被中斷時，畫面會回到「以目前投影為準」的狀態，不會卡在半途

## 10. `@tool` 與編輯器工具（只有寫編輯器工具時適用）

- [ ] 用 `Engine.is_editor_hint()` 區分編輯器與遊戲
- [ ] 產生節點時設定正確 `owner`；支援 Undo／Redo
- [ ] 不在 Setter 或 `_process()` 中重建整棵樹

## 11. PackedScene 載入

- [ ] 高頻生成物（金幣粒子、傷害數字、骰子）的 PackedScene 用 `preload()` 或快取
- [ ] 大型場景（酒館桌面、神殿特寫）用背景載入，載入中畫面持續更新
- [ ] 不在 `_process()` 中載入資源

## 12. UI（Control、Container、Anchor）

主螢幕是**電視、距離約 3 公尺**；手機 UI 在 React，不在 Godot。

- [ ] HUD（四角玩家面板）放在 CanvasLayer，不跟著地圖鏡頭縮放
- [ ] 放進 Container 的 Control 不依賴手動 Position
- [ ] 純裝飾 Control 的 Mouse Filter 設為 Ignore
- [ ] 720p、1080p、4K 電視輸出都測過；16:9 為主，21:9 不裁切關鍵資訊
- [ ] 字型、Theme 集中設定，不散在各節點
- [ ] 主螢幕文字在 3 公尺外可讀（最小字級 ⚠️ 依美術規範定）

## 13. AnimationPlayer 不是規則來源

- [ ] 動畫只負責「看起來」；何時扣血、扣多少一律來自伺服器事件
- [ ] 動畫名稱集中管理；動畫被中斷時一定會送出完成回報或被 Presenter 收尾
- [ ] 3D 骰子停下的點數等於伺服器結果（技術規劃 §3）

## 14. `class_name` 與靜態型別

- [ ] `class_name` 只給真正可重用的類型（`PlayerPanel`、`CardView`、`DiceView`、產生的 DTO）
- [ ] 公開函式、成員、Signal 參數全部有型別；網路資料一律用 `protocol-codegen` 產生的類別
- [ ] GDScript Warning 規則全隊統一，不大量忽略

## 15. Scene 繼承

- [ ] Inherited Scene 不超過兩層；差異優先用元件組合或 Resource 參數

## 16. 效能（Profiler）

- [ ] 用 Debugger → Profiler 量最重的演出：4 人同時數值變化＋卡牌翻出＋粒子
- [ ] 看 Frame Time，不只看平均 FPS；記錄偶發卡頓（第一次載入 Shader）
- [ ] 用 Monitors／ObjectDB 確認：連玩 10 局後節點數回到合理範圍（沒有演出節點洩漏）
- [ ] 在最低規格 Windows 電腦實測

## 17. 本專案專屬

- [ ] 只有 Godot 4 語法（AGENTS §4 第 9 條）
- [ ] 所有 WebSocket 訊息帶 `protocolVersion`；版本不符時顯示拒絕畫面
- [ ] Godot 不計算任何遊戲數值（例如不自己算起點收入、不自己判定勝負）
- [ ] 地圖格子位置由「格子順序＋外形」計算，不手擺
- [ ] 斷線重連後先套用快照，再播之後的事件

## 發布前最重要的 10 項

1. 固定 Godot 版本，發布前不升級
2. 可重用 Scene 不依賴外部 NodePath
3. Autoload 只有 5 個
4. Resource 不存執行中數值
5. `await` 之後重新檢查節點
6. `queue_free()` 之後不再操作
7. 演出可被新快照中斷並正確收尾
8. 主螢幕在 3 公尺外可讀
9. 用 Profiler 量過最重的演出
10. 匯出的正式版在乾淨的 Windows 上完整玩過一局

# 03｜美術 × 玩法決策流程（命運酒館版）

> 來源：使用者提供的「美術與玩法權重衝突」與「團隊決策流程」（2026-11-24），依本專案改寫。
> 本專案的特殊條件：
> - **美術由人工製作**（2026-11-24 決定），不使用 AI 生成最終美術；AI 工具只負責程式與文件。
> - 主螢幕是電視，玩家坐在約 3 公尺外，而且**一邊喝酒一邊玩**；手機負責私密資訊與操作。
> - 一局目標 2.5 小時：**演出時間也是預算**，每多 1 秒的演出，一局累積多好幾分鐘。
> - 原文中的動作遊戲衝突（攻擊前搖、Hitbox、碰撞）不適用；改成本專案會遇到的衝突類型（第 3 節）。

---

## 1. 核心原則

**玩法決定玩家要看見什麼，美術決定玩家如何看見；美術可以強化玩法，但不能隱藏、延遲或誤導玩法資訊。**

衝突時依序保護：

1. 玩家知道**現在輪到誰、要做什麼**
2. 玩家看得懂**剛剛發生了什麼**（數值變化、卡牌結果、勝負）
3. 一局維持在 2.5 小時 ±20%
4. 核心特色成立（醉意、塔羅、派對互動）
5. 美術風格與情緒
6. 效能（最低規格 Windows）與製作時程

### 不可犧牲項目

- [ ] 3 公尺外看得清四角玩家面板的生命、金幣、清醒值（U1）
- [ ] 卡牌在電視上只顯示**結果**，不要求大家讀完整卡面文字（U2）
- [ ] 每次數值變化都有「誰、變多少」的視覺回饋，不只靠顏色
- [ ] 演出不遮住目前行動的玩家與棋盤位置
- [ ] 單一演出有時長上限（第 4 節），可以被演出速度設定加速
- [ ] 不公開的資訊不會因為美術演出而洩漏（例如手牌外觀、大牌卡背）
- [ ] 喝醉的玩家也能看懂（大字、高對比、不依賴細節）

## 2. 角色與決策權

| 角色 | 負責 | 本專案 |
|---|---|---|
| 設計負責人 | 玩家什麼時候需要看見什麼；資訊層級；演出時長預算 | 你 |
| 美術負責人 | 風格、色彩、版面、動畫姿勢、資產品質與工時 | 小黃（也負責 3D、骨架動畫、Godot 場景與特效） |
| 工程負責人 | Godot 實作、效能、演出佇列、修改成本與回退 | 你（Godot 連線與演出框架）；場景內實作成本由小黃估 |
| 最終裁決人 | 依本流程裁決並記錄代價 | 你（2026-11-25）。你同時是設計與工程負責人，所以裁決一律照第 5 節否決條件與評分表打分，分數寫進紀錄；小黃對美術品質有否決權時要寫明理由 |

- 美術可以自行決定：色彩細節、材質、裝飾、次要動畫、不影響資訊層級的特效。
- 工程可以自行決定：演出佇列實作、效能上限、資源載入方式。
- **必須共同決定**：主螢幕版面與資訊層級、演出時長、卡牌結果的呈現方式、3D 演出的使用範圍、低畫質時保留哪些效果。

## 3. 本專案會遇到的衝突類型

| 類型 | 例子 | 預設方向 |
|---|---|---|
| 演出時長 vs 節奏 | 大牌翻牌想做 5 秒的華麗演出 | 遵守第 4 節時長預算；華麗版放在「第一次出現」或高潮時刻 |
| 華麗演出 vs 資訊可讀 | 聖物登場特效蓋住玩家面板 | 面板與棋盤永遠在最上層；特效讓位 |
| 卡面美術 vs 電視可讀 | 精緻插畫縮小後看不出是哪張牌 | 電視上用大標題＋結果數字；完整卡面只在手機 |
| 風格一致 vs 互動提示 | 可停留的特殊格和裝飾長得太像 | 每種格子固定的形狀與圖示語言，不只靠顏色 |
| 場景氣氛 vs 狀態辨識 | 昏暗酒館光影讓中毒、監獄圖示看不清 | 狀態圖示一律高對比、固定位置 |
| 3D 演出 vs 時程與效能 | 每種卡都想要 3D 翻牌 | 3D 只用在骰子、翻牌、聖物登場（技術規劃 T7） |
| 資產品質 vs 製作時程 | 39 張卡面插畫拖慢 M4 | 灰盒版用佔位；先做**風格切片**（與 M3～M4 平行）定案風格，再大量生產卡面 |

## 4. 演出時長預算（2026-11-24 確認；數值為硬性上限，灰盒測試後只能經決策單調整）

**總帳**：2.5 小時＝9,000 秒；4 人局約 37 回合 × 4 人 ≈ 148 次行動 → 每次行動平均約 60 秒。**系統演出平均每次行動 ≤ 20 秒**，其餘留給選擇、反應窗、現實喝酒與聊天。

| 演出 | 上限 | 說明 |
|---|---|---|
| 擲骰（3D）＋移動 | 3 秒＋每格 0.2 秒，最多 5 秒 | 每次行動都有，最常出現；近失演出也包含在這 5 秒內 |
| 格子事件標題 | 1.5 秒 | — |
| 盲選牌背（手機選牌＋主螢幕翻開） | 選牌時間不計；翻開 1.5 秒 | 2026-11-25 加入；洗牌演出 ≤ 2 秒（一局約 3 次） |
| 卡牌結果（小牌、冥界事件） | 3 秒 | 一局約 60 次 |
| 試煉攻防開場、結果 | 3 秒、4 秒 | 不含小遊戲本身（準備 3＋對決約 10 秒） |
| 大牌打出 | 4 秒 | 同一張牌第一次出現可 6 秒 |
| 拍賣、賭場 | 依互動時間，演出部分 ≤ 3 秒 | — |
| 死亡 | 8 秒 | 一局只出現幾次，可以華麗 |
| 復活 | 6 秒 | — |
| 聖物登場 | 8 秒 | — |
| 勝利 | 20 秒 | 遊戲已結束，不影響時長 |
| 反應窗 | 每層 5 秒，全員回應即關閉 | 不是演出，但最容易吃掉時間：8 秒×前後兩窗會讓一局多約 40 分鐘 |

- 每加 1 秒到「最常出現」的演出，一局約多 2～3 分鐘；改動前先算這筆帳。超過預算的演出，必須從別的演出扣回來。
- 驗收：M8 灰盒遙測（M8-A11）。

## 5. 決策流程

```
發現衝突 → 建立決策單 → 是否觸及不可犧牲項目？
  ├─ 是 → 玩法資訊優先，改美術方案
  └─ 否 → 提出最多 3 個方案 → 否決檢查 → 加權評分
           ├─ 差距明確 → 裁決
           └─ 差距 ≤ 25 分 → 做最小比較版本 → 試玩 → 裁決
→ 記錄接受的代價與回退條件 → 整合、驗收
```

### 5-1 決策單

```
議題名稱：            提出日期：        提出人：
設計／美術／工程負責人：            最終裁決人：
影響畫面（畫面清單編號 H__／P__）：
玩家正在做什麼？
玩家需要看見什麼？
目前發生什麼問題？
證據：□ 試玩影片 □ 試玩紀錄 □ Godot Profiler □ 演出時長量測 □ 美術稿
```

### 5-2 否決條件（任一成立就不進入評分）

- [ ] 3 公尺外看不清面板數值或目前行動的玩家
- [ ] 演出超過第 4 節上限且無法加速
- [ ] 洩漏不公開資訊
- [ ] 低畫質會刪除必要資訊
- [ ] 最低規格電腦 Frame Time 超過 33 ms（30 FPS）
- [ ] 工期超過目前里程碑剩餘時間，且沒有降級方案

### 5-3 加權評分（每項 1～5 分，滿分 500）

| 項目 | 權重 |
|---|---|
| 資訊可讀性（電視、3 公尺、喝醉也看得懂） | 25 |
| 節奏影響（演出時長、等待感） | 20 |
| 美術風格與情緒 | 15 |
| 是否強化遊戲特色（醉意、塔羅、派對） | 15 |
| 技術穩定性 | 10 |
| 效能 | 5 |
| 製作與修改成本 | 5 |
| 後續擴充性（非 MVP 卡牌、更多職業） | 5 |

- 400 以上直接採用；350～399 修正後採用；300～349 做比較版本測試；低於 300 不採用。
- 兩方案相差 ≤ 25 分：不用會議投票，做比較版本試玩。

### 5-4 比較版本與試玩

- 只改一個變因（例如卡牌結果呈現方式），其他（種子、牌序、人數）相同。
- 時間盒：UI 版面 2～4 小時；單一演出 0.5～1 天。
- 3～5 人快速試玩即可；記錄「是否能說出剛剛誰發生了什麼」「是否覺得等太久」，不要只問「哪個好看」。
- 門檻建議：80% 測試者能正確說出剛剛的結果；沒有人覺得同一種演出「太長、想跳過」。

### 5-5 決策紀錄

```
採用方案：        決定日期：        決策人：
採用理由：
接受的代價：□ 美術衝擊降低 □ 演出變長 □ 工時增加 □ 效能成本 □ 其他
被拒絕方案與原因：
回退條件（例：試玩辨識率低於 __%、一局時長超過 __ 分鐘）：
重新檢查時間：□ 下一次試玩 □ 灰盒版 □ 風格切片 □ 指定日期
```

## 6. 會議（30 分鐘內）

| 時間 | 內容 |
|---|---|
| 0～5 分 | 設計：玩家要看見什麼、目前造成什麼失敗 |
| 5～10 分 | 美術：美術意圖、哪些是風格核心、哪些可以調 |
| 10～15 分 | 工程：Godot 實作、效能、工時、回退成本 |
| 15～25 分 | 否決檢查、評分、決定要不要做比較版本 |
| 25～30 分 | 指定方案與負責人、期限、驗收門檻、回退條件 |

- 會後：決策寫進專案文件；被取代的資產不直接刪除，保留可回退版本。

## 7. 10 分鐘內可以自己決定的事

- 不影響資訊層級的色彩、材質、裝飾、次要粒子、背景小動畫。

## 8. 一定要走流程的事

- 主螢幕版面、四角面板、資訊層級
- 任何會改變演出時長的修改
- 卡牌、格子、狀態圖示的視覺語言
- 3D 演出的範圍
- 低畫質模式要刪掉哪些效果
