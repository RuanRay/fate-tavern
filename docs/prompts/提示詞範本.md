# 提示詞範本（vibe coding 用）

> 2026-11-25：實作用 Claude Code、審查用 Gemini 網頁版（見 `docs/prompts/AI工具與上下文.md`）。以下範本 §1～§5 給 Claude Code；§6 改為給 Gemini 審查的打包方式。
> 原說明：Claude Code、Gemini CLI 會自動讀 repo 裡的規範檔；**ChatGPT 網頁版沒有 repo 存取時**，每次對話開頭要貼上 `AGENTS.md`＋階段文件＋相關設計章節＋要修改的檔案內容（見第 6 節）。

---

## 1. 新功能（一個需求 ID）

```
【任務】___（需求 ID：M_-R__）
【必讀】AGENTS.md；docs/phases/___.md 第 __ 節；docs/design/___.md 第 __ 節
【範圍】只能修改：___（資料夾或檔案）
【要求】
1. 先輸出計畫：要改的檔案、函式簽名、資料結構、測試案例清單；等我回覆「確認」才開始寫。
2. 測試先行（規則、協定、資料庫類變更必須）。
3. 實作後執行 pnpm typecheck && pnpm lint && pnpm test（Godot 另跑 GUT），貼出結果。
4. 依 .github/pull_request_template.md 輸出 PR 說明。
5. 設計文件沒寫清楚或互相矛盾時，用【需要決定】格式停下來問我。
【驗收】對應的驗收條件：M_-A__
【禁止】超出範圍修改；新增執行期依賴；修改 docs/design/；為了通過測試而修改測試預期值。
```

## 2. 修 Bug

```
【問題】___（重現步驟、預期結果、實際結果、相關日誌或事件 ID）
【必讀】AGENTS.md；相關階段文件與設計章節
【要求】
1. 先寫一個能重現問題的失敗測試（優先用黃金重播劇本）。
2. 說明根本原因（不是症狀）。
3. 最小修正；不順便重構。
4. 確認沒有其他地方有同樣的問題，列出搜尋過的位置。
【禁止】修改測試預期值來讓測試通過，除非證明測試本身與設計文件不符（附章節）。
```

## 3. 重構

```
【目標】___（為什麼要重構：可讀性／效能數據／重複程式）
【限制】行為完全不變：重構前後的黃金重播與全部測試結果一致；不改公開介面（或列出所有呼叫點）。
【要求】先給計畫與分步驟（每步可以單獨合併）。
```

## 4. 補測試

```
【對象】___（模組或需求 ID）
【要求】
1. 依設計文件 ___ 章節列出所有規則分支與邊界。
2. 對照現有測試，列出缺口。
3. 補測試；每個測試名稱註明對應的設計文件章節。
4. 如果新測試失敗，**不要修改實作**，回報失敗原因給我判斷。
```

## 5. 內容轉檔（設計文件 → YAML）

```
【任務】把 docs/design/___.md 第 __ 節的 ___ 轉成 content/___.yaml＋測試
【要求】
1. 只轉指定範圍。
2. 每個數值後面用註解標出來源章節。
3. 現有效果元件表達不了的效果，列出來問我，不要自己寫 scripted handler。
4. 最後輸出「設計文件 vs YAML」對照表。
【禁止】修改或「修正」任何數值。
```

## 6. Gemini 網頁版審查的上下文打包

> 2026-11-25 起用 `pnpm review-pack <PR> --focus general|rules-security|content` 自動產生（AI 工具與上下文 §4-2），下面的手動格式只在工具還沒做好時使用。

每次新對話先貼：

```
以下是專案規範與本次任務需要的文件，請先讀完再回覆「已讀」，不要開始寫程式。
=== AGENTS.md ===
（貼全文）
=== docs/phases/M_.md（只貼相關章節）===
=== docs/design/___.md（只貼相關章節）===
=== 要修改的檔案 ===
（貼檔案全文，標明路徑）
```

- 回覆的程式碼一律以「完整檔案＋路徑」或「unified diff」輸出，方便貼回 repo。
- 對話太長時開新對話，用第 7 節交接範本接續。

## 7. 交接範本（換工具、換對話、隔天繼續）

```
## 交接
- 日期：
- 階段與需求 ID：
- 目前分支／PR：
- 已完成：
- 進行中（做到哪一步）：
- 下一步：
- 已知問題與待決定事項：
- 這次對話中做的決定（附理由）：
- 需要先讀的檔案：
```
