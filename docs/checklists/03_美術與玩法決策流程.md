# 03｜美術 × 玩法決策流程（命運酒館版）

> 來源：使用者提供的「美術與玩法權重衝突」與「團隊決策流程」（2026-11-24），依本專案改寫。
> 本專案的特殊條件：
> - **美術由人工製作**（2026-11-24 決定），不使用 AI 生成最終美術；AI 工具只負責程式與文件。
> - 主螢幕是電視，玩家坐在約 3 公尺外，而且**一邊喝酒一邊玩**；手機負責私密資訊與操作。
> - 一局目標 2.5 小時：**演出時間也是預算**，每多 1 秒的演出，一局累積多好幾分鐘。
> - 原文中的動作遊戲衝突（攻擊前搖、Hitbox、碰撞）不適用；改成本專案會遇到的衝突類型（第 3 節）。

---

## 1. 核心原則

**玩法決定玩家要看見什麼，美術決定玩家如何看見；美術可以強化玩法，但不能隱藏、延遲或誤導玩法資訊。**

衝突時依序保護：

1. 玩家知道**現在輪到誰、要做什麼**
2. 玩家看得懂**剛剛發生了什麼**（數值變化、卡牌結果、勝負）
3. 一局維持在 2.5 小時 ±20%
4. 核心特色成立（醉意、塔羅、派對互動）
5. 美術風格與情緒
6. 效能（測試筆電；不做低規格測試）與製作時程

### 不可犧牲項目

- [ ] 3 公尺外看得清四角玩家面板的生命、金幣、清醒值（U1）
- [ ] 卡牌在電視上只顯示**結果**，不要求大家讀完整卡面文字（U2）
- [ ] 每次數值變化都有「誰、變多少」的視覺回饋，不只靠顏色
- [ ] 演出不遮住目前行動的玩家與棋盤位置
- [ ] 單一演出有時長上限（第 4 節），可以被演出速度設定加速
- [ ] 不公開的資訊不會因為美術演出而洩漏（例如手牌外觀、大牌卡背）
- [ ] 喝醉的玩家也能看懂（大字、高對比、不依賴細節）

## 2. 角色與決策權

| 角色 | 負責 | 本專案 |
|---|---|---|
| 設計負責人 | 玩家什麼時候需要看見什麼；資訊層級；演出時長預算 | 你 |
| 美術負責人 | 風格、色彩、版面、動畫姿勢、資產品質與工時 | 小黃（也負責 3D、骨架動畫、Godot 場景與特效） |
| 工程負責人 | Godot 實作、效能、演出佇列、修改成本與回退 | 你（Godot 連線與演出框架）；場景內實作成本由小黃估 |
| 最終裁決人 | 依本流程裁決並記錄代價 | 你（2026-11-25）。你同時是設計與工程負責人，所以裁決一律照第 5 節否決條件與評分表打分，分數寫進紀錄；小黃對美術品質有否決權時要寫明理由 |

- 美術可以自行決定：色彩細節、材質、裝飾、次要動畫、不影響資訊層級的特效。
- 工程可以自行決定：演出佇列實作、效能上限、資源載入方式。
- **必須共同決定**：主螢幕版面與資訊層級、演出時長、卡牌結果的呈現方式、3D 演出的使用範圍、低畫質時保留哪些效果。

## 3. 本專案會遇到的衝突類型

| 類型 | 例子 | 預設方向 |
|---|---|---|
| 演出時長 vs 節奏 | 大牌翻牌想做 5 秒的華麗演出 | 遵守第 4 節時長預算；華麗版放在「第一次出現」或高潮時刻 |
| 華麗演出 vs 資訊可讀 | 聖物登場特效蓋住玩家面板 | 面板與棋盤永遠在最上層；特效讓位 |
| 卡面美術 vs 電視可讀 | 精緻插畫縮小後看不出是哪張牌 | 電視上用大標題＋結果數字；完整卡面只在手機 |
| 風格一致 vs 互動提示 | 可停留的特殊格和裝飾長得太像 | 每種格子固定的形狀與圖示語言，不只靠顏色 |
| 場景氣氛 vs 狀態辨識 | 昏暗酒館光影讓中毒、監獄圖示看不清 | 狀態圖示一律高對比、固定位置 |
| 3D 演出 vs 時程與效能 | 每種卡都想要 3D 翻牌 | 3D 只用在骰子、翻牌、聖物登場（技術規劃 T7） |
| 資產品質 vs 製作時程 | 39 張卡面插畫拖慢 M4 | 灰盒版用佔位；先做**風格切片**（與 M3～M4 平行）定案風格，再大量生產卡面 |

## 4. 演出時長預算（2026-11-24 確認；數值為硬性上限，灰盒測試後只能經決策單調整）

**總帳**：2.5 小時＝9,000 秒；4 人局約 37 回合 × 4 人 ≈ 148 次行動 → 每次行動平均約 60 秒。**系統演出平均每次行動 ≤ 20 秒**，其餘留給選擇、反應窗、現實喝酒與聊天。

| 演出 | 上限 | 說明 |
|---|---|---|
| 擲骰（3D）＋移動 | 3 秒＋每格 0.2 秒，最多 5 秒 | 每次行動都有，最常出現；近失演出也包含在這 5 秒內 |
| 格子事件標題 | 1.5 秒 | — |
| 盲選牌背（手機選牌＋主螢幕翻開） | 選牌時間不計；翻開 1.5 秒 | 2026-11-25 加入；洗牌演出 ≤ 2 秒（一局約 3 次） |
| 卡牌結果（小牌、冥界事件） | 3 秒 | 一局約 60 次 |
| 試煉攻防開場、結果 | 3 秒、4 秒 | 不含小遊戲本身（準備 3＋對決約 10 秒） |
| 大牌打出 | 4 秒 | 同一張牌第一次出現可 6 秒 |
| 拍賣、賭場 | 依互動時間，演出部分 ≤ 3 秒 | — |
| 死亡 | 8 秒 | 一局只出現幾次，可以華麗 |
| 復活 | 6 秒 | — |
| 聖物登場 | 8 秒 | — |
| 勝利 | 20 秒 | 遊戲已結束，不影響時長 |
| 反應窗 | 每層 5 秒，全員回應即關閉 | 不是演出，但最容易吃掉時間：8 秒×前後兩窗會讓一局多約 40 分鐘 |

- 每加 1 秒到「最常出現」的演出，一局約多 2～3 分鐘；改動前先算這筆帳。超過預算的演出，必須從別的演出扣回來。
- 驗收：M8 灰盒遙測（M8-A11）。

## 5. 決策流程

```
發現衝突 → 建立決策單 → 是否觸及不可犧牲項目？
  ├─ 是 → 玩法資訊優先，改美術方案
  └─ 否 → 提出最多 3 個方案 → 否決檢查 → 加權評分
           ├─ 差距明確 → 裁決
           └─ 差距 ≤ 25 分 → 做最小比較版本 → 試玩 → 裁決
→ 記錄接受的代價與回退條件 → 整合、驗收
```

### 5-1 決策單

```
議題名稱：            提出日期：        提出人：
設計／美術／工程負責人：            最終裁決人：
影響畫面（畫面清單編號 H__／P__）：
玩家正在做什麼？
玩家需要看見什麼？
目前發生什麼問題？
證據：□ 試玩影片 □ 試玩紀錄 □ Godot Profiler □ 演出時長量測 □ 美術稿
```

### 5-2 否決條件（任一成立就不進入評分）

- [ ] 3 公尺外看不清面板數值或目前行動的玩家
- [ ] 演出超過第 4 節上限且無法加速
- [ ] 洩漏不公開資訊
- [ ] 低畫質會刪除必要資訊
- [ ] 測試筆電 Frame Time 超過 33 ms（30 FPS）
- [ ] 工期超過目前里程碑剩餘時間，且沒有降級方案

### 5-3 加權評分（每項 1～5 分，滿分 500）

| 項目 | 權重 |
|---|---|
| 資訊可讀性（電視、3 公尺、喝醉也看得懂） | 25 |
| 節奏影響（演出時長、等待感） | 20 |
| 美術風格與情緒 | 15 |
| 是否強化遊戲特色（醉意、塔羅、派對） | 15 |
| 技術穩定性 | 10 |
| 效能 | 5 |
| 製作與修改成本 | 5 |
| 後續擴充性（非 MVP 卡牌、更多職業） | 5 |

- 400 以上直接採用；350～399 修正後採用；300～349 做比較版本測試；低於 300 不採用。
- 兩方案相差 ≤ 25 分：不用會議投票，做比較版本試玩。

### 5-4 比較版本與試玩

- 只改一個變因（例如卡牌結果呈現方式），其他（種子、牌序、人數）相同。
- 時間盒：UI 版面 2～4 小時；單一演出 0.5～1 天。
- 3～5 人快速試玩即可；記錄「是否能說出剛剛誰發生了什麼」「是否覺得等太久」，不要只問「哪個好看」。
- 門檻建議：80% 測試者能正確說出剛剛的結果；沒有人覺得同一種演出「太長、想跳過」。

### 5-5 決策紀錄

```
採用方案：        決定日期：        決策人：
採用理由：
接受的代價：□ 美術衝擊降低 □ 演出變長 □ 工時增加 □ 效能成本 □ 其他
被拒絕方案與原因：
回退條件（例：試玩辨識率低於 __%、一局時長超過 __ 分鐘）：
重新檢查時間：□ 下一次試玩 □ 灰盒版 □ 風格切片 □ 指定日期
```

## 6. 會議（30 分鐘內）

| 時間 | 內容 |
|---|---|
| 0～5 分 | 設計：玩家要看見什麼、目前造成什麼失敗 |
| 5～10 分 | 美術：美術意圖、哪些是風格核心、哪些可以調 |
| 10～15 分 | 工程：Godot 實作、效能、工時、回退成本 |
| 15～25 分 | 否決檢查、評分、決定要不要做比較版本 |
| 25～30 分 | 指定方案與負責人、期限、驗收門檻、回退條件 |

- 會後：決策寫進專案文件；被取代的資產不直接刪除，保留可回退版本。

## 7. 10 分鐘內可以自己決定的事

- 不影響資訊層級的色彩、材質、裝飾、次要粒子、背景小動畫。

## 8. 一定要走流程的事

- 主螢幕版面、四角面板、資訊層級
- 任何會改變演出時長的修改
- 卡牌、格子、狀態圖示的視覺語言
- 3D 演出的範圍
- 低畫質模式要刪掉哪些效果
