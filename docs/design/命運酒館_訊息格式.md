## 1. 基本原則

| # | 原則 |
|---|---|
| P1 | **伺服器權威**：客戶端只送「我想做什麼」（Command），合法與否、結果是什麼，一律由伺服器決定 |
| P2 | **結果帶絕對值**：事件裡的數值變化同時給「變化量」與「變化後的值」（例如 `delta: -10, after: 85`），客戶端直接套用，**不需要也不准自己計算規則** |
| P3 | **只送該看的**：不公開的資料在伺服器端就過濾掉，不會出現在不該看的裝置的封包裡 |
| P4 | **可重送、不重複**：每個命令都帶唯一 `messageId`，同一個 ID 重送時，伺服器回傳第一次的結果，不會執行兩次 |
| P5 | **有序**：伺服器送給每個連線的訊息都帶遞增的 `seq`；客戶端發現跳號就要求補發 |
| P6 | **先寫入、再回覆**：命令產生的事件寫入 PostgreSQL 成功後，才送 `command.accepted` 與廣播 |
| P7 | **時間以伺服器為準**：所有倒數、截止時間都用伺服器時間（毫秒），客戶端用時鐘校正換算 |
| P8 | **文字不進協定**：協定只傳 ID 與數值（例如 `cardId: "minor.swords.10"`），顯示文字由各端的語系檔查表 |

## 2. 連線與身分

### 2-1 角色

| 角色 `role` | 裝置 | 看得到 | 能送的命令 |
|---|---|---|---|
| `host` | 主螢幕（Godot） | 公開資訊 | 開房、開始對局、演出完成回報、房主控制（暫停、移除裝置） |
| `player` | 手機 | 公開資訊＋自己的私人資訊＋偷看到的資訊 | 遊戲操作、回應輸入請求、小遊戲輸入、喝酒確認 |
| `admin` | 管理後台 | 全部（含私人資訊與事件紀錄） | 覆寫、轉移主螢幕、測試控制（回滾、審計查詢 MVP 不做） |
| `spectator` | 預留（異地觀戰） | 公開資訊 | 無 |

### 2-2 HTTP 端點（Fastify）

| 方法 | 路徑 | 用途 | 回傳 |
|---|---|---|---|
| POST | `/api/v1/rooms` | 主螢幕開房 | `roomId`、`roomCode`（6 碼短碼）、`hostSessionToken`、`joinUrl` |
| GET | `/api/v1/rooms/{roomId}/qr` | 取得加入用 QR Code 圖片（PNG） | 圖片；內容為 `joinUrl?t={joinToken}` |
| POST | `/api/v1/rooms/{roomCode}/join` | 手機用 Join Token 或短碼加入 | `playerId`、`sessionToken`、`wsUrl` |
| POST | `/api/v1/admin/login` | 管理後台登入 | `adminSessionToken` |
| GET | `/api/v1/health` | 健康檢查 | `ok` |

- **Join Token**：高熵、一次性、⚠️ 10 分鐘過期；用過就失效。
- **短碼**：6 碼英數，搭配速率限制（同一 IP 每分鐘 ⚠️ 10 次）。
- **Session Token**：加入後換發，存在手機瀏覽器（localStorage）與主螢幕本機；用來連 WebSocket 和斷線重連。房主可以撤銷。

### 2-3 WebSocket 端點

```
wss://{host}/ws?protocolVersion=1
```

- 連上後第一個訊息必須是 `session.hello`（見第 5 節），帶 Session Token；5 秒內沒送就斷線。
- Token 不放在網址參數，避免出現在伺服器日誌。

## 3. 信封（Envelope）

所有 WebSocket 訊息都是一個 JSON 物件，外層固定：

```json
{
  "protocolVersion": 1,
  "messageType": "command.roll_dice",
  "messageId": "01JD2Z8K6Q4N9V3T7W5X1Y0A2B",
  "roomId": "rm_8f3k2p",
  "seq": 128,
  "ackSeq": 127,
  "causationId": null,
  "sentAt": 1764000000123,
  "payload": {}
}
```

| 欄位 | 型別 | 方向 | 必填 | 說明 |
|---|---|---|---|---|
| `protocolVersion` | 整數 | 雙向 | ✅ | 目前為 `1` |
| `messageType` | 字串 | 雙向 | ✅ | `分類.名稱`，例如 `command.roll_dice`、`event.batch` |
| `messageId` | 字串（ULID） | 雙向 | ✅ | 唯一 ID；命令的冪等鍵 |
| `roomId` | 字串 | 雙向 | ✅ | 房間 ID；`session.hello` 之前可以是空字串 |
| `seq` | 整數 | 雙向 | ✅ | 發送方在這條連線上的遞增序號（從 1 開始，重連後延續伺服器那一側的序號） |
| `ackSeq` | 整數 | 雙向 | 選填 | 已收到對方的最後一個連續序號 |
| `causationId` | 字串或 null | 伺服器 → 客戶端 | 選填 | 這則訊息是由哪個命令（`messageId`）造成的 |
| `sentAt` | 整數（毫秒） | 雙向 | ✅ | 發送時間；伺服器訊息為伺服器時間 |
| `payload` | 物件 | 雙向 | ✅ | 依 `messageType` 而定 |

- 單一訊息上限 ⚠️ 64 KB；超過就拒絕（`error.payload_too_large`）。
- 客戶端遇到**不認識的欄位要忽略**，不能報錯（見第 16 節）。

## 4. 訊息分類總表

| 分類 | 方向 | 用途 | 主要訊息 |
|---|---|---|---|
| `session.*` | 雙向 | 握手、心跳、重連、離線 | `hello`、`welcome`、`resume`、`ping`、`pong`、`kicked`、`closing` |
| `command.*` | 客戶端 → 伺服器 | 遊戲操作 | `roll_dice`、`use_item`、`use_magic_die`、`play_major`、`use_skill`、`respond`、`buy`、`bid`、`bet`、`confirm_drink`、`end_turn` … |
| `command.accepted`／`command.rejected` | 伺服器 → 客戶端 | 命令結果 | — |
| `prompt.*` | 伺服器 → 客戶端 | 請玩家做決定 | `request`、`update`、`closed` |
| `event.*` | 伺服器 → 客戶端 | 已發生的事（已寫入資料庫） | `batch` |
| `projection.*` | 伺服器 → 客戶端 | 完整狀態或校驗 | `snapshot`、`checksum` |
| `presentation.*` | 雙向 | 主螢幕演出與節奏 | `sequence`（伺服器 → 主螢幕）、`completed`、`skipped`（主螢幕 → 伺服器） |
| `minigame.*` | 雙向 | 小遊戲 | `prepare`、`ready`、`start`、`input`、`state`、`submit`、`resolved` |
| `clock.*` | 雙向 | 時鐘校正 | `ping`、`pong` |
| `admin.*` | 雙向（只限 admin） | 管理 | `override`、`host_transfer`、`test_control`（`rollback_*`、`audit_query` MVP 不做） |
| `error.*` | 伺服器 → 客戶端 | 協定層錯誤 | `protocol_mismatch`、`invalid_message` … |

## 5. 連線生命週期

### 5-1 握手

```
客戶端                                   伺服器
  │── session.hello ───────────────────▶│  驗證 Token、版本
  │◀──────────────── session.welcome ───│  身分、伺服器時間、心跳設定
  │◀─────────────── projection.snapshot ─│  完整狀態（依角色過濾）
  │◀──────────────── prompt.request ────│  若有尚未回應的請求，重新送出
```

`session.hello`

```json
{
  "role": "player",
  "sessionToken": "st_…",
  "clientInfo": { "app": "mobile-web", "build": "0.1.0+a1b2c3", "locale": "zh-TW" },
  "resume": null
}
```

`session.welcome`

```json
{
  "playerId": "pl_03",
  "role": "player",
  "serverTime": 1764000000123,
  "heartbeatIntervalMs": 5000,
  "heartbeatTimeoutMs": 15000,
  "contentVersion": "content@2026.11.24-01",
  "stateVersion": 412
}
```

- `contentVersion`：卡牌資料版本；客戶端用來確認自己的語系與圖片包是否對得上。
- `stateVersion`：目前事件序號（每寫入一個領域事件 +1）。

### 5-2 心跳

- 客戶端每 `heartbeatIntervalMs`（預設 5 秒）送 `session.ping`；伺服器回 `session.pong`。
- 伺服器超過 `heartbeatTimeoutMs`（預設 15 秒）沒收到任何訊息，就判定斷線：玩家狀態改為「離線」，座位保留 3 分鐘（見設定）。
- **主螢幕**的逾時為 **10 秒**；判定斷線後對局自動暫停（`game.paused`，`reason: host_disconnected`），規則見《技術規劃》§12-3。重連後收到 `projection.snapshot`，5 秒倒數後自動 `game.resumed`。

### 5-3 斷線重連

`session.hello` 的 `resume` 欄位：

```json
{ "lastServerSeq": 127, "lastStateVersion": 410 }
```

| 情況 | 伺服器做法 |
|---|---|
| 缺少的訊息還在伺服器的重送緩衝區（⚠️ 最近 500 則） | 依序補發 `seq` 128 之後的訊息 |
| 超出緩衝區，或伺服器重啟過 | 送新的 `projection.snapshot`，客戶端整個替換狀態 |
| Session Token 已被撤銷或座位已釋出 | `session.kicked`，原因 `seat_released` |

- **伺服器重啟**：伺服器從「快照＋事件」重建後，所有客戶端重連都拿到 `projection.snapshot`，並附 `stateHash` 讓客戶端記錄（崩潰恢復測試用它比對）。

### 5-4 結束

- `session.closing`：伺服器要關閉（部署、維護），附 `reason` 與 `reconnectAfterMs`。
- `session.kicked`：被房主移除或 Token 失效，附 `reason`。

## 6. 命令（Command）與回覆

### 6-1 流程

```
command.*  →  驗證格式（Zod） → 驗證身分與時機 → 規則驗證 → Reducer → 事件寫入 DB
           →  command.accepted（給送命令的人）
           →  event.batch（依可見性分送給所有人）
           →  presentation.sequence（給主螢幕）
```

- 每個房間的命令**依收到順序串行處理**。
- 同一 `messageId` 重送：伺服器直接回傳第一次的 `accepted` 或 `rejected`，不重複執行。

### 6-2 回覆

`command.accepted`

```json
{
  "commandId": "01JD2Z8K6Q4N9V3T7W5X1Y0A2B",
  "stateVersion": 413,
  "eventIds": ["ev_000413"]
}
```

`command.rejected`

```json
{
  "commandId": "01JD2Z8K6Q4N9V3T7W5X1Y0A2B",
  "code": "not_your_turn",
  "detail": { "currentPlayerId": "pl_01" }
}
```

- 被拒絕的命令**不產生事件、不扣成本**。

### 6-3 命令清單（MVP）

| `messageType` | 誰可以送 | `payload` 重點欄位 | 說明 |
|---|---|---|---|
| `command.start_game` | host | `seed?`（只限測試模式） | 開始對局 |
| ~~`command.choose_class`~~ | — | — | 2026-11-25 改成輸入請求 `choose_class`，用 `command.respond` 回應（訊息欄位表 E3） |
| `command.roll_dice` | player | `throwStrength?: "soft"｜"normal"｜"hard"`（手機搖骰的力道；按按鈕＝`normal`） | 擲移動骰（輪到自己時）；力道只影響主螢幕的動畫軌跡，不影響點數 |
| `command.respond` | player | `promptId`、`choice` | 回應輸入請求（見第 7 節） |
| `command.use_item` | player | `itemInstanceId`、`targets?` | 使用道具（主動時機） |
| `command.use_magic_die` | player | `dieInstanceId`、`rollId`、`targets?` | 在擲骰前後窗口使用魔術骰子；通常透過 `command.respond` 送，這是保留的直接入口 |
| `command.play_major` | player | `majorInstanceId`、`timing: "turn_start"｜"turn_end"` | 打出塔羅大牌（反應時機走 `command.respond`） |
| `command.use_skill` | player | `skillId`、`targets?`、`options?` | 小技能或大招 |
| ~~`command.buy`~~ | — | — | 2026-11-25 改成輸入請求 `shop`，用 `command.respond` 回應（訊息欄位表 E3） |
| `command.alchemy` | player | `itemInstanceId` | 煉金工坊升級 |
| `command.bid` | player | `auctionId`、`amount` | 拍賣出價 |
| `command.bet` | player | `casinoRoundId`、`option`、`amount` | 賭場下注 |
| `command.trade_offer` | player | `toPlayerId`、`give`、`want` | 提出交易（聖杯騎士等） |
| `command.confirm_drink` | player | `drinkRequestId` | 酒精版「喝了」確認 |
| `command.end_turn` | player | — | 結束行動（有可選動作時） |
| `command.pause_game`／`command.resume_game` | host | `reason?` | 房主暫停／繼續 |
| `command.kick_device` | host | `playerId` | 移除裝置（撤銷 Session Token） |

- **目標**一律用 ID：`{ "playerIds": ["pl_02"] }`、`{ "cellIndex": 17 }`。
- 道具、骰子、大牌用「實例 ID」（`it_…`、`md_…`、`mj_…`），不用種類 ID，因為同一種可能有好幾張。

## 7. 輸入請求（Prompt）

需要玩家決定的地方，規則引擎會暫停並發出 `prompt.request`；只送給被要求回應的人（主螢幕收到公開的摘要，用來顯示「等待某某選擇」）。

### 7-1 `prompt.request`

```json
{
  "promptId": "pr_000231",
  "kind": "reaction_window",
  "forPlayerIds": ["pl_02", "pl_03", "pl_04"],
  "context": { "eventId": "ev_000420", "sourceCardId": "major.tower", "depth": 0 },
  "options": [
    { "optionId": "pass", "label": "opt.pass" },
    { "optionId": "use:md_0091", "label": "opt.use_magic_die", "ref": { "magicDieId": "die.amulet" } },
    { "optionId": "play:mj_0007", "label": "opt.play_reaction_major", "ref": { "majorId": "major.tower" } }
  ],
  "min": 1,
  "max": 1,
  "defaultOptionId": "pass",
  "deadlineAt": 1764000008123,
  "responseMode": "in_turn_order"
}
```

| 欄位 | 說明 |
|---|---|
| `kind` | 請求種類，見下表 |
| `forPlayerIds` | 誰要回應；每支手機只會收到含自己的請求 |
| `options` | 合法選項（**伺服器已經過濾過，客戶端不判斷合法性**）；`label` 是語系鍵 |
| `min`／`max` | 可選數量（例如投票選 1 人、選 2 個目標） |
| `defaultOptionId` | 逾時自動採用的選項 |
| `deadlineAt` | 截止的伺服器時間（一般 20 秒；反應窗 5 秒）。對局暫停時凍結，恢復後重新計算並送 `prompt.update` |
| `responseMode` | `any`（同時回應）、`in_turn_order`（依回合順序，一人回應完才輪下一人）、`all`（全部回應完才繼續） |

### 7-2 `kind` 種類

| `kind` | 用在 | 例子 |
|---|---|---|
| `choose_option` | 二選一、三選一 | 聖杯九許願、寶劍二蒙眼抉擇、錢幣二周轉 |
| `choose_target` | 選玩家、選格子、選手牌 | 寶劍七（清醒可指定）、愚者正位瞬移、聖杯七（清醒自選棄牌） |
| `blind_pick` | 從牌庫盲選 | 選項＝牌背位置 `slot:0`～`slot:3`（剩不到 4 張就更少）；`max` 依雙子座等為 1 或 2；`defaultOptionId`＝`slot:0`；**選項不含任何牌的資訊** |
| `deck_peek` | 地圖殘頁：先選要偷看的牌背位置，看完再選「放最底部／留著」 | 第二步的牌面只送給本人（`visibility: owner`） |
| `reaction_window` | 反應鏈（最多 2 層） | 護符骰、反應大牌（高塔逆、惡魔逆）、反魔法護符、解酒草 |
| `pre_roll_window`／`post_roll_window` | 擲骰前後的魔術骰子窗口 | 巨人骰、鉛心骰、翻轉骰、詛咒骰 |
| `accept_risk` | 要不要冒險 | 權杖國王逆「孤注一擲」、聖杯九逆、膽小鬼之外的押注 |
| `bet` | 下注金額與選項 | 賭場、佩斯洛旁觀者下注 |
| `vote` | 投票 | 瑪納茲、寶劍國王逆 |
| `trade_response` | 接受或拒絕交易 | 聖杯騎士「提議」 |
| `lethal_protection` | 致命保護有多個可用時，選用哪一個 | 不老聖杯 vs 死神逆 |
| `confirm_drink` | 酒精版喝酒確認 | 所有喝酒事件 |
| `shop` | 商城購買（可多次回應直到離開） | 普通商城、冥界商店 |
| `choose_class` | 開局選職業 | 輪流選、不重複 |
| `templar_number` | 聖殿騎士選 D8 數字 | 開局、祭壇改數字 |

### 7-3 回應與更新

- 玩家用 `command.respond` 回應：`{ "promptId": "pr_000231", "choice": ["use:md_0091"] }`。
- `prompt.update`：同一個請求的狀態變化（例如依回合順序輪到下一人、截止時間延長），主螢幕用來更新「等待中」的顯示。
- `prompt.closed`：請求結束，附 `reason: "answered" | "timeout" | "cancelled"` 與最後採用的選項（只給相關的人）。
- 逾時：伺服器以 `defaultOptionId` 代為回應，並記錄一個 `prompt_timed_out` 事件（遙測用）。
- **提前關閉**：`forPlayerIds` 裡的人全部回應後，請求立即以 `reason: "answered"` 關閉，不等截止時間。
- **反應類請求不洩漏持有物**（`pre_roll_window`、`post_roll_window`、`reaction_window`，2026-11-24 確認）：
  - 收件者＝依規則**可以**回應的所有活人，不論手上有沒有可用的牌；沒有可用選項的人只收到「不使用」。
  - 主螢幕的等待提示只顯示「等待回應中」與倒數，**不顯示是誰還沒回應**，也不顯示已回應人數。
  - 伺服器端不因為「沒有人有可用的牌」而跳過窗口；所有人都回應後，窗口至少顯示 1.5 秒才關閉。
  - 手機的「自動略過」開關（預設開啟）：沒有可用選項時由手機自動回「不使用」（W8）。
  - 擲骰後窗口同時送給所有可回應的人（`responseMode: all`），收齊後依回合順序加入反應鏈（W9）。

### 7-4 喝酒確認（酒精版）

- 喝酒事件產生後，伺服器對要喝的玩家送 `prompt.request`（`kind: "confirm_drink"`），附 `cups` 與 `drinkRequestId`。
- **遊戲數值（清醒值）在事件發生時就已扣除**，確認只是記錄「現實有沒有喝」，不影響規則結算，也不會卡住遊戲流程；逾時記為 `unconfirmed`（遙測用）。

## 8. 領域事件（Event）與可見性

### 8-1 `event.batch`

一個命令可能產生好幾個領域事件；伺服器把同一命令造成的事件包成一批，**依每個收件者的可見性過濾後**分別送出。

```json
{
  "fromStateVersion": 413,
  "toStateVersion": 416,
  "events": [
    {
      "eventId": "ev_000414",
      "stateVersion": 414,
      "eventType": "dice.rolled",
      "eventVersion": 1,
      "occurredAt": 1764000001200,
      "visibility": "public",
      "data": { "rollId": "rl_0088", "playerId": "pl_01", "purpose": "move", "dieType": "d8", "raw": 3, "final": 3, "modifiers": [] }
    },
    {
      "eventId": "ev_000415",
      "stateVersion": 415,
      "eventType": "player.moved",
      "eventVersion": 1,
      "occurredAt": 1764000001200,
      "visibility": "public",
      "data": { "playerId": "pl_01", "from": 9, "to": 12, "path": [10, 11, 12], "passedStart": false, "lap": 1 }
    },
    {
      "eventId": "ev_000416",
      "stateVersion": 416,
      "eventType": "resource.changed",
      "eventVersion": 1,
      "occurredAt": 1764000001200,
      "visibility": "public",
      "data": { "playerId": "pl_01", "resource": "gold", "delta": 30, "after": 75, "reason": { "kind": "start_income" } }
    }
  ]
}
```

- 收件者看不到的事件**整個不送**，或改送遮蔽版（見 8-3）；所以 `stateVersion` 對某個客戶端來說可能有空號，這是正常的。客戶端用 `toStateVersion` 更新自己記錄的版本。
- 每個事件的 `data` 都帶**變化後的值**，客戶端直接套用到 Projection Store。

### 8-2 可見性等級

| `visibility` | 誰收到完整內容 | 例子 |
|---|---|---|
| `public` | 所有人 | 移動、生命、金幣、清醒值、狀態、擲骰結果、公開的卡牌 |
| `owner` | 擁有者（`ownerId`）＋admin | 抽到道具、魔術骰子、大牌、聖殿騎士選定的數字 |
| `peek` | 偷看的人（`viewerIds`）＋admin | 寶劍王牌、寶劍侍者偷看手牌；權杖二偷看星座 |
| `admin` | 只有 admin | 牌庫順序、隨機數種子、內部稽核 |

### 8-3 遮蔽版事件（redacted）

不能看內容、但應該知道「有事發生」的人，收到遮蔽版：

```json
{
  "eventType": "hand.changed_privately",
  "visibility": "public",
  "redacted": true,
  "data": { "playerId": "pl_02", "reason": { "kind": "shop_purchase" } }
}
```

- 例：pl_02 在商城買了道具。依設定總表「資訊公開規則」，**手牌數量與內容都不公開**，所以主螢幕與其他人只收到 `hand.changed_privately`（知道他的手牌有變動、原因是買東西），不含種類與數量；pl_02 自己收到完整的 `hand.item_gained`。
- 道具「使用時短暫揭露」：`hand.item_used` 是公開事件，含道具種類。
- 偷看事件對被偷看的人：只收到「某某偷看了你」（`peek.performed`），不含看到的內容。

### 8-4 事件類型清單（MVP 第一版）

| 分類 | `eventType` | `data` 重點 |

## 10. 演出序列（Presentation）

主螢幕不懂規則，只照伺服器的「劇本」播放。

### 10-1 `presentation.sequence`（伺服器 → 主螢幕）

```json
{
  "sequenceId": "sq_000177",
  "causationEventIds": ["ev_000414", "ev_000415", "ev_000416"],
  "steps": [
    { "stepId": 1, "kind": "focus_player", "playerId": "pl_01" },
    { "stepId": 2, "kind": "dice_roll", "rollId": "rl_0088", "dieType": "d8", "result": 3, "style": "physics_3d", "strength": "normal", "trajectoryHint": 17, "nearMiss": null },
    { "stepId": 3, "kind": "move_token", "playerId": "pl_01", "path": [10, 11, 12] },
    { "stepId": 4, "kind": "float_text", "playerId": "pl_01", "resource": "gold", "delta": 30 },
    { "stepId": 5, "kind": "card_reveal", "cardId": "minor.swords.10", "orientation": "upright", "tier": "tipsy", "style": "flip_3d" }
  ],
  "maxDurationMs": 9000,
  "blocking": true
}
```

| 欄位 | 說明 |
|---|---|
| `steps` | 依序播放的步驟；同一個 `stepId` 可以有多個步驟同時播放（例如全場同時扣血） |
| `trajectoryHint` | 3D 骰子要用哪一條預錄軌跡（由伺服器的種子隨機數決定，重播時畫面也一樣）；主螢幕再把骰面數字對應到 `result` |
| `maxDurationMs` | 這段演出最長多久；伺服器據此設定保底計時 |
| `blocking` | `true`：播完才開放下一個輸入；`false`：背景播放（例如狀態圖示更新） |

### 10-2 演出步驟 `kind`（第一版）

`focus_player`、`camera`、`dice_roll`、`dice_modify`、`move_token`、`teleport`、`swap_positions`、`card_reveal`、`card_effect`、`float_text`、`bar_change`、`status_icon`、`damage_hit`、`heal`、`drink`、`death`、`revive`、`soul_fire`、`zodiac_change`、`duel_intro`、`minigame_view`、`duel_result`、`auction_view`、`casino_view`、`relic_reveal`、`banner`、`wait`、`deck_shuffle`、`blind_pick_view`（4 張牌背與被選的那張）

- `dice_roll` 的 `strength` 決定軌跡類別；`nearMiss` 不是 null 時為 `{ "teeterFace": 6 }`，主螢幕播放在該面邊緣搖晃再倒向 `result` 的軌跡（伺服器已確認兩面幾何相鄰、只依公開資訊）。

- 每種步驟的欄位定義在 `packages/protocol/presentation/*.ts`。
- 主螢幕遇到**不認識的步驟就跳過**，並回報 `presentation.skipped`（含 `stepId` 與原因），不能卡住。

### 10-3 節奏控制

- 主螢幕播完一段 `blocking` 序列後送 `presentation.completed { "sequenceId": "sq_000177" }`。
- 伺服器收到後才送出下一個 `prompt.request`（或讓下一位玩家行動）。
- **保底**：主螢幕仍在線、但超過 `maxDurationMs + 3000` 毫秒還沒收到完成回報（例如演出卡住），伺服器自動當作完成，避免整局卡死。主螢幕**斷線**時不走保底，改為暫停對局（§5-2）；暫停期間保底計時也凍結。
- 房主可以設定演出速度（`1x`／`1.5x`／`2x`），主螢幕依倍率縮短時間；伺服器的保底時間依同樣倍率計算。⚠️ 速度設定的入口待定（主螢幕或後台）。
- 手機端不需要等演出；但手機的「輪到你了」提示會等主螢幕演出完才出現（跟著 `prompt.request` 一起到）。

## 11. 小遊戲

### 11-1 流程

```
伺服器                     參加者手機                        主螢幕
 │── minigame.prepare ───▶│（載入、校時）                     │
 │── minigame.prepare ──────────────────────────────────────▶│（準備觀戰畫面）
 │◀── minigame.ready ─────│
 │── minigame.start（startAt）──▶ 全部 ─────────────────────▶│
 │◀── minigame.input（即時對抗類，每 100 ms）
 │── minigame.state ───────────────────────────────────────▶│（拔河繩子位置）
 │◀── minigame.submit（分數＋操作紀錄）
 │── minigame.resolved ──▶ 全部
```

### 11-2 `minigame.prepare`

```json
{
  "minigameRunId": "mg_0042",
  "gameId": "minigame.tug_of_war",
  "format": "2v1",
  "teams": [ { "teamId": "A", "playerIds": ["pl_01","pl_03"] }, { "teamId": "B", "playerIds": ["pl_02"] } ],
  "durationMs": 10000,
  "prepareMs": 3000,
  "params": { "lineDistance": 100 },
  "myModifiers": [ { "kind": "war_horn", "effect": "tap_power_plus_25" } ]
}
```

- 題目種子**不在 `prepare` 送**，改在 `minigame.start` 才送（見 11-3；2026-11-25 確認）。
- `myModifiers`：只送給本人、會影響他手機畫面的加成（例如戰吼號角讓點酒單「多看一次」、鍛鐵「甜蜜點加寬」）；**計分用的加成（例如二對一 ×1.5）不送，由伺服器結算時套用**。
- 主螢幕收到的版本沒有 `myModifiers`。

### 11-3 開始時間

- `minigame.start { "startAt": 1764000020000, "seed": "3f9a…（32 位十六進位）" }`：伺服器時間；各端用時鐘校正換算成本地時間後同時開始。
- `seed`：讓需要隨機內容的小遊戲（符文辨識的出現順序、點酒單的酒名、數金幣的數量）**所有參加者看到同樣的題目**，也能重播；手機用 `packages/protocol` 匯出的同一套 ChaCha20 產生題目。
- 送出時間至少比 `startAt` 早 ⚠️ 1500 毫秒，讓網路慢的手機也來得及。

### 11-4 輸入與結算

| 類型 | 遊戲 | 手機送什麼 |
|---|---|---|
| 各自計分 | 符文辨識、點酒單、鍛鐵、停錶、數金幣 | 結束時 `minigame.submit { score, inputLog }` |
| 反應比快 | 拔劍決鬥 | 每回合 `minigame.submit { round, reactionMs, falseStart }`（本地計時：從畫面出現訊號到按下） |
| 即時對抗 | 拔河 | 每 100 ms `minigame.input { tick, taps }`；伺服器累計並送 `minigame.state` 給主螢幕 |
| 同時出招 | 符文猜拳、膽小鬼 | `minigame.submit { round, move }` 或 `{ releasedAtMs }`；伺服器到齊後揭曉 |

- `inputLog`：操作的時間點與內容（例如每次點擊的本地毫秒），伺服器用來檢查是否像人（反作弊）與灰盒分析；上限 ⚠️ 2000 筆。
- 逾時沒送：視為最低分（或該回合判負）。
- 平手時伺服器送 `minigame.tiebreak { round }` 開始加賽（流程同 `start`，帶新的 `startAt` 與 `seed`），最多一次；加賽仍平手由系統擲（小遊戲規格 §1-5）。
- `minigame.resolved`：公開的勝負、各隊分數、`tiebreakStage`（`none`／`game_rule`／`extra_round`／`system_roll`）（已套用二對一係數與戰吼加成），接著伺服器產生 `duel.resolved` 等領域事件。

## 12. 時鐘校正

- 連線後、每場小遊戲前，客戶端連續送 ⚠️ 5 次 `clock.ping { "t0": 本地時間 }`。
- 伺服器回 `clock.pong { "t0": …, "serverTime": … }`。
- 客戶端用往返時間最短的那一次計算時差：`offset = serverTime − (t0 + t1) / 2`（`t1` 為收到時的本地時間）。
- 之後所有 `deadlineAt`、`startAt` 都換算成 `本地時間 = 伺服器時間 − offset`。

| ~~`admin.rollback_preview`~~（**MVP 不做**，2026-11-25 簡化後端） | 預覽回滾 | `targetEventId`（最近 20 個完整事件內）；回傳回滾後的狀態摘要與 `confirmToken` |

## 14. 錯誤代碼

### 14-1 協定層（`error.*`，通常會斷線）

| 代碼 | 說明 | 客戶端處理 |
|---|---|---|
| `error.protocol_mismatch` | `protocolVersion` 不相容 | 顯示「請更新」畫面，附 `minSupported`、`latest` |
| `error.invalid_message` | JSON 格式或 Envelope 不合格 | 記錄後丟棄；連續 ⚠️ 10 次就斷線 |
| `error.unauthorized` | Token 無效或過期 | 回到加入畫面 |
| `error.payload_too_large` | 超過大小上限 | 記錄 |
| `error.rate_limited` | 送太快 | 依 `retryAfterMs` 等待 |
| `error.server_restarting` | 伺服器重啟中 | 依 `reconnectAfterMs` 重連 |

### 14-2 命令層（`command.rejected` 的 `code`）

| 代碼 | 說明 |
|---|---|
| `not_your_turn` | 不是你的行動時機 |
| `invalid_phase` | 目前階段不能做這件事 |
| `invalid_target` | 目標不合法 |
| `insufficient_resource` | 金幣、清醒值等不足 |
| `on_cooldown` | 技能冷卻中 |
| `limit_reached` | 次數用完（每回合 1 張大牌、每場攻防 1 個攻擊或防禦道具、每次擲骰每人 1 顆魔術骰子） |
| `prompt_expired` | 請求已截止 |
| `prompt_not_for_you` | 這個請求不是給你的 |
| `invalid_choice` | 選項不在 `options` 裡 |
| `reaction_depth_exceeded` | 反應鏈已達 2 層 |
| `item_not_owned` | 不是你的道具或骰子 |
| `dead_player_restricted` | 死亡玩家不能做這件事 |
| `game_paused` | 對局暫停中 |
| `game_over` | 對局已結束 |
| `content_mismatch` | 客戶端的內容版本跟伺服器不同 |
| `test_mode_only` | 這個操作只能在測試模式的對局使用 |
| `internal_error` | 伺服器內部錯誤（附 `traceId`，對局不受影響） |

## 15. 資料型別與命名

| 項目 | 規則 |
|---|---|
| 編碼 | UTF-8 JSON |
| 欄位名稱 | `camelCase` |
| `messageType`、`eventType` | `分類.名稱`，名稱用 `snake_case` |
| 列舉值 | 小寫 `snake_case`（`upright`、`reversed`、`sober`、`tipsy`、`drunk`） |
| 時間 | 整數毫秒（UTC，伺服器時間）；**不用字串日期** |
| 數值 | 全部整數：生命、金幣、魂火、清醒值（0～100 的整數百分比）、傷害；百分比加成用整數（`25` 表示 +25%） |
| 實例 ID | 字串，帶前綴：房間 `rm_`、玩家 `pl_`、事件 `ev_`、請求 `pr_`、擲骰 `rl_`、演出 `sq_`、小遊戲 `mg_`、道具實例 `it_`、魔術骰子實例 `md_`、大牌實例 `mj_`、效果 `fx_`、Session Token `st_` |
| 內容 ID | 跟 YAML 一致的點號路徑：`minor.swords.10`、`trial.fehu`、`major.tower`、`item.whetstone`、`die.amulet`、`zodiac.libra`、`class.templar`、`relic.philosopher_stone`、`minigame.tug_of_war` |
| `messageId` | ULID（26 字元，可依時間排序） |
| 文字 | 協定只傳語系鍵（例如 `opt.pass`），各端查語系檔；只有玩家暱稱是原文 |
| 空值 | 用 `null`，不要省略必填欄位；選填欄位可以省略 |

## 16. 版本與相容

| 變更 | 做法 |
|---|---|
| 新增選填欄位、新增事件類型、新增演出步驟、新增選項 | **不升版**；舊客戶端忽略不認識的欄位、跳過不認識的步驟 |
| 改欄位意義、刪除欄位、改必填 | **升 `protocolVersion`** |
| 事件結構改變 | 提高該事件的 `eventVersion`，伺服器用 Upcaster 轉換舊紀錄 |

- 伺服器同時支援目前版本與前一版（`minSupported = latest − 1`）。⚠️ MVP 階段可以只支援單一版本。
- `protocolVersion` 不符時：伺服器回 `error.protocol_mismatch` 並斷線；客戶端顯示「請更新主程式／重新整理網頁」。
- 部署順序：伺服器先上（同時支援新舊）→ 手機網頁 → 主螢幕；回滾時順序相反。

## 18. 契約測試與程式產生

```
packages/protocol/
├─ src/
│  ├─ envelope.ts          信封
│  ├─ session.ts           session.*
│  ├─ commands/*.ts        各命令的 payload
│  ├─ prompts.ts           prompt.*
│  ├─ events/*.ts          各事件的 data（含 eventVersion）
│  ├─ projection.ts        projection.*
│  ├─ presentation/*.ts    演出步驟
│  ├─ minigame.ts          minigame.*
│  ├─ admin.ts             admin.*
│  ├─ errors.ts            錯誤代碼
│  └─ hash.ts              stateHash 演算法
├─ examples/               每種訊息至少 1 個合法、1 個不合法的 JSON 範例
└─ dist/
   ├─ schema/*.json        由 Zod 產生的 JSON Schema
   └─ godot/*.gd           由 tools/protocol-codegen 產生的 GDScript 類別
```

- **單一來源**：只在 Zod 寫一次 → 產生 JSON Schema → 產生 TS 型別與 GDScript 類別（含 `from_dict()`／`to_dict()`）。不准手寫第二份。
- **契約測試**（CI 必跑）：
  - 伺服器：每個 `examples/*.valid.json` 都能通過 Zod；`*.invalid.json` 都被拒絕。
  - 手機與後台：同一批範例能被 TS 型別讀取。
  - Godot（GUT）：同一批範例能被產生的 GDScript 類別讀取並轉回相同 JSON。
- **破壞性變更檢查**：PR 時比對新舊 JSON Schema，有破壞性變更但 `protocolVersion` 沒升，就讓 CI 失敗。
- **黃金重播**：固定種子＋一串命令，產生的事件序列與 `stateHash` 必須跟存檔一致。
- **崩潰恢復**：對局中強制結束伺服器 → 重啟 → 用原 Session Token 重連 → `projection.snapshot` 的 `stateHash` 與中斷前一致。
