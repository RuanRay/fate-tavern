## 3. Godot 端規範（靜態型別 GDScript）

```
Godot 主程式
├── GDScript：場景、UI、動畫、音效
├── GDScript：WebSocket Client
├── GDScript：Projection Store
├── GDScript：輸入與房主控制
└── C++ GDExtension：只作效能預留，不先導入
```

```gdscript
# 採用
var room_id: String
var connected: bool = false
var players: Array[PlayerProjection] = []

func connect_to_room(join_token: String) -> void:
	pass

func apply_event(event: ServerEvent) -> void:
	pass
```

```gdscript
# 不採用：重要資料全部用 Variant
var room
var players = []
func handle_message(message):
	pass
```

**工程規則**

1. 公開函式必須標記參數與回傳型別。
2. 網路 DTO 必須有明確型別。
3. 禁止 Godot 客戶端自行決定合法性。
4. Godot 只送出 Command，不直接修改權威狀態。
5. 伺服器回傳 Event 或 Projection 後，Godot 才更新顯示。
6. Autoload 只放基礎服務，不放全部遊戲邏輯。
7. 所有亂數結果由伺服器產生。
8. 不在 GDScript 複製 TypeScript 規則。
9. 先用 Godot Profiler 找出瓶頸，再討論 C++。
10. Godot 與伺服器的訊息都要帶 `protocolVersion`。
11. **AI 輔助規範**：AI 開發規範檔明文鎖定「只允許 Godot 4.x API，禁止 Godot 3 語法」（例如 Tween 用 `create_tween()`、`@onready`、新版 `WebSocketPeer`）。

**Godot 端補充**

- QR Code 由伺服器用 `qrcode` 套件產生圖片傳給 Godot 顯示。
- 地圖格子做成獨立場景，執行時依格子順序排成正多邊形（4 人局正七邊形）。
- 主螢幕視覺：**2.5D 插畫風**（斜俯視的酒館木桌與羊皮紙地圖、分層視差、Shader 光效、粒子、鏡頭縮放）。
- **局部 3D**：常見動畫用 3D 模型或 3D 視窗疊在 2D 畫面上（例如擲骰滾動、塔羅翻牌、聖物登場）；資訊面板、數值、地圖格子維持 2D，確保電視上看得清楚。
- 3D 只做「播放用的演出」：骰子點數一律由伺服器決定。

**3D 骰子的物理演出（採用「物理演出、結果預定」）**

| 做法 | 說明 | 判定 |
|---|---|---|
| 物理決定結果（Godot 主螢幕擲） | 主螢幕的物理模擬決定點數 | ❌ 違反「亂數由伺服器產生」；不同電腦的物理結果不保證一致，無法重播；主螢幕可以被竄改 |
| 伺服器跑物理 | 伺服器用確定性物理引擎模擬，把軌跡送給主螢幕播放 | ⚠️ 可行但過度工程：多一套物理引擎、傳送軌跡資料，派對遊戲不需要 |
| **物理演出、結果預定** | 伺服器先決定點數；主螢幕用真的物理（或預錄的軌跡）讓骰子滾動，再把骰面數字對應到「最後朝上的那一面＝伺服器的點數」 | ✅ 採用：看起來是真的物理、結果仍由伺服器決定、可以重播 |

- 實作：先離線預錄一批真實物理的擲骰軌跡（每種骰子 D4／D6／D8／D12／D20 各數十條），記下每條最後朝上的是哪一面。播放時隨機挑一條，**在開始滾動前**把數字貼圖重新對應，讓朝上的那一面剛好是伺服器的點數。數字排法照真實骰子的規則（例如 D8 對面相加為 9），旋轉對應後仍是合法的骰子。
- 好處：每次播放都穩定、可預測時長（配合 15 秒節奏與演出佇列），不會出現骰子卡在牆角、滾太久的情況。
- 魔術骰子：擲骰後修改結果時（鉛心骰 ±1、翻轉骰、重擲等），播放「骰子發光翻面」或重新擲一次的演出，最後停在修改後的點數。
- **力道分類（2026-11-25）**：預錄軌跡分成「輕滾、一般、猛甩」三類；手機搖骰的力道（或按鈕＝一般）隨 `command.roll_dice` 送出，伺服器用「演出亂數流」從該類挑軌跡。力道**只影響動畫，不影響點數**。
- **近失演出（2026-11-25）**：另外預錄「在某一面邊緣搖晃後倒向另一面」的軌跡。只用在設定檔列出的高風險擲骰（卡面標「爆發」的擲骰、賭場系統擲骰等），而且只在「差一面就是另一種結果」時使用；搖晃的面必須和最終面在骰子上**幾何相鄰**（D8 對面相加為 9，例如 4 和 5 是對面，不能做 4↔5 的近失），沒有合法相鄰面就不做。搖晃面只能依公開資訊決定，**不能用在聖殿騎士的選定數字**（會洩漏私密資訊）。近失軌跡也受擲骰演出上限 5 秒限制。
- 「即時物理」也可以：骰子在主螢幕即時用物理滾，停下後由程式把朝上面的數字換成伺服器點數（滾動中用動態模糊遮掩）。但時長與落點不可控，建議只在預錄軌跡不夠用時再考慮。

## 4. 伺服器與規則

### 4-1 不可妥協的處理管線

```
Command
→ Auth／Schema Validation
→ Rule Validation
→ Deterministic Reducer
→ Domain Events
→ Transactional Event Write（寫入 PostgreSQL）
→ Projection Update
→ Client Broadcast
```

**禁止**

- Godot 或手機自行決定命令是否合法。
- 用 `Math.random()` 產生未記錄的亂數。
- 只把房間權威狀態存在 Node.js 記憶體。
- 在 WebSocket Handler 裡直接寫大量卡牌規則。
- 用 `eval()` 執行 YAML 裡的效果程式碼。

### 4-2 規則引擎

- 狀態欄位照《命運酒館_遊戲狀態模型》v1.0（Zod 定義、可見性、不變量）。
- 純函式 Reducer；時間與亂數由輸入帶入（種子隨機數），同一顆種子＋同一串命令＝同一局結果。
- **獨立亂數流（2026-11-25）**：對局種子衍生多條亂數流，每個機制只用自己的那一條（見第 12-5 節）；某個機制多抽一次亂數，不會改變其他機制的結果。
- 流程照《命運酒館_規則優先序》第 2 節的 A → B → C 階段狀態機；每個子效果結算後檢查死亡；整個事件（含後續觸發）結算完才檢查勝利。
- **反應鏈深度 2** 寫進規則資料與測試；超過直接拒絕。
- 傷害管線：承受者 → 替代基礎傷害 → 百分比 → 固定值 → 減傷 → 上限 30 → 免疫 → 扣血 → 致命保護 → 死亡判定。

### 4-3 卡牌內容：YAML＋受控效果元件

```yaml
# 寶劍十正位（《MVP卡牌v4》§1-1）；名稱與描述走語系鍵，不寫在 YAML
id: minor.swords.10
kind: minor_card
orientation: upright
effects:
  - type: lose_hp          # 扣血＝代價／自傷，不走傷害管線
    target: self
    amount: 10
  - type: drink
    target: others
    cups: 1
tiers:
  sober:
    extra:
      - type: transfer_gold
        from: others
        to: self
        amount: 5
  drunk:
    override:
      - { type: lose_hp, target: self, amount: 15 }
      - { type: drink, target: others, cups: 2 }
```

- 效果只能由**受控元件**組成；元件表達不了時，才呼叫經過測試的伺服器端 TS Handler：

```yaml
effects:
  - type: scripted
    handler: relic.spear_of_fate.v1
```

- 禁止：`script: "player.hp -= Math.random() * 10"`。
- YAML 在 CI 中編譯成 JSON artifact；規則 ID 永不重用。
- 需要 scripted handler 的已知效果（2026-11-24 v4 後）：只剩永恆之槍「命定天罰」與祭司大招的翻牌流程；卡牌全部由受控元件表達（元件清單見《命運酒館_MVP卡牌v4》第 6 節與開發包 `docs/design/效果元件對照表.md`）。

### 4-4 協定

> 完整規格見《命運酒館_訊息格式》v1（信封、連線、命令、輸入請求、事件可見性、狀態投影、演出序列、小遊戲、時鐘校正、管理後台、錯誤代碼、版本相容、契約測試）。

每個訊息的 Envelope：

```json
{
  "protocolVersion": 1,
  "messageType": "command.play_card",
  "messageId": "uuid",
  "roomId": "room-id",
  "payload": {}
}
```

- 自訂序號、ACK、心跳、重連；每個房間的 Command 串行處理；訊息帶冪等鍵，可以重送。
- 重連後伺服器回傳最新 Projection。
- 資訊過濾：主螢幕只收公開 Projection；手機收「公開＋自己的私人資訊」；不公開的資料**不送到不該看的裝置**。
- 向後相容政策、舊版拒絕畫面、JSON Schema 契約測試、三端共用協定範例。

### 4-5 事件儲存與快照

- 每個完整 Domain Event 都寫入 PostgreSQL；**寫入成功後才回覆命令成功**。
- 每個行動結束或每 30 個事件建立快照，附狀態雜湊（M1-R07；`SNAPSHOT_EVERY_EVENTS`）。
- 伺服器重啟後從「快照＋後續事件」重建。
- Event Type 版本化（Upcaster）；錯誤用補償事件處理，不刪除資料。

### 4-6 房主覆寫與回滾

> 2026-11-25 簡化後端：**MVP 不做回滾**，以下回滾規則保留作為之後的設計；覆寫照做。

- 可以回滾最近 **20 個完整事件**。
- 原事件永久保留；回滾建立 `rollback_applied` 事件，記錄操作者、理由、時間、目標事件、前後狀態雜湊。
- 回滾前向所有玩家顯示提示；不允許回滾到無法通過 Schema／Invariant 的狀態。
- 房主操作要二次確認；管理路由與玩家路由分開、需要認證。

### 4-7 事件結算引擎（實作草案 v1.0，依「事件結算引擎」流程圖）

> 原則：**先驗證，再反應，再結算；勝利在完整事件結束後檢查。**

**A. 主流程**

1. 接收事件 → 安全／連線檢查（需要暫停時：暫停並保存事件，恢復後回到檢查）。
2. 建立事件快照：來源、目標、階段、成本、效果。
3. 檢查時機、目標、次數、成本是否合法；不合法則拒絕事件、不扣成本。
4. 支付成本、消耗使用次數。
5. 呼叫 B：反應鏈。
6. 原事件被取消 → 保留已付成本、記錄取消。沒被取消 → 重新驗證目標、鎖定特例與替代效果；仍有合法效果才依卡面逐項（或明示同時）結算，否則失效、不退成本。
7. 傷害呼叫 C；其他資源與狀態直接結算；每項之後呼叫 D：死亡／復活檢查。
8. 子效果都處理完 → 依回合順序處理後續觸發，直到觸發佇列清空。
9. **完整事件結束 → 檢查勝利**；達成則結束對局並保存紀錄，否則回到下一行動階段。

- 被取消或失效的事件，仍要先清完它已經造成的死亡或觸發，再檢查勝利。

**B. 反應鏈**

- 深度 d 從 0 開始；d < 2 且有人合法回應時，依回合順序選下一位回應者，驗證、支付成本、推入反應堆疊，d＋1。
- 結束後由後往前結算，回傳「原事件取消／繼續」。
- 只能回應卡面允許的效果；禁止把一般取消牌當成通用反制。成本與勝利檢查不能被取消。

**C. 傷害**

- 先分類：攻擊／持續／環境；生命成本另走失血流程（例如清醒反噬）。
- 決定代防、轉移後的承受者。
- 套用明確的基礎傷害替代（例如 D6）→ 計算倍率、固定加減、減傷 → 取整、最低 0、套上限 → 檢查免疫（免疫此類傷害則傷害＝0）→ 扣除生命（順序照《規則優先序》§6）。

```
D = clamp( floor( B × M + F − R ), 0, 上限 )
B 基礎、M 倍率（同類百分比相加）、F 固定修正、R 減傷
```

**D. 死亡與復活**

- 生命 ≤ 0：有可用的致命保護時，由本人選一項、消耗並設定生命；仍 ≤ 0 就重新檢查（避免無效保護循環）。
- 沒有保護：死亡當下反應窗（審判等明示例外）→ 能立即復活就依效果設定生命與狀態；不能就提交死亡：清理資產、大牌、聖物，進入死神追逐。
- 同時傷害：先批次扣血，再處理所有玩家的保護與死亡，最後才交回主流程檢查勝利。
- 回血不等於復活；只有明示的立即復活可以先於資產清理。

**執行規範**

1. 來源不決定優先權；明確特例只覆寫指定條文。
2. 每個事件有唯一 ID；每個替代效果在同一事件最多套用一次。
3. 暫停行動仍推進計時；額外移動不算新行動。
4. 未決規則進入設定表，不得用流程圖偷偷定案。

**與現有文件的差異（✅ 2026-11-23 已確認，照建議處理）**

| # | 項目 | 流程圖 | 現有文件 | 建議 |

### 7-1 開發環境（2026-11-25 確認）

**環境劃分**：伺服器啟動時讀 `APP_ENV`（`local`／`ci`／`staging`／`production`），所有設定用 Zod 驗證，缺一項就拒絕啟動。

| 環境 | 用途 | 伺服器 | 資料庫 | 手機網頁、後台 | 祕密從哪裡來 | 對局模式 |
|---|---|---|---|---|---|---|
| `local` | 每位成員的電腦 | `pnpm dev` | Docker Compose 的 PostgreSQL | Vite 開發伺服器（區網 HTTPS，見下方） | `.env.local`（不進 repo；範本 `.env.example`） | 測試＋正式 |
| `ci` | GitHub Actions | 測試程式內啟動 | Actions 的 PostgreSQL 服務容器（每次全新） | Playwright 對本機建置 | 不需要祕密 | 測試 |
| `staging` | 封測、遠端展示 | Fly.io 小型主機（短期展示可用 Render Free） | Neon（獨立專案，不和正式共用） | Cloudflare Pages 預覽網址 | GitHub Environments＋Fly secrets | 測試＋正式 |
| `production` | 灰盒測試（M8）與公開 MVP | 常駐付費主機 | 託管 PostgreSQL，每日備份 | Cloudflare Pages 正式網址 | 主機的祕密管理 | **只有正式**（`ALLOW_TEST_MODE=false`） |

- 每個環境的資料庫、管理密碼、Token 簽章金鑰都**各自獨立**；伺服器啟動時檢查資料庫名稱帶有環境名，對不上就拒絕啟動。
- 正式環境的資料不複製到較低的環境；需要分析時只匯出遙測 CSV（匿名 ID）。

**區網 HTTPS（真手機測試必備）**

- iOS 只有在 HTTPS（安全連線）頁面上才能使用動作感測（搖手機擲骰），`http://192.168.x.x` 會完全用不了；所以本機開發一律走 HTTPS。
- 預設做法：**mkcert**。
  - 在開發機產生本機憑證，`pnpm dev` 的 Vite 與 Fastify 都用它。
  - 加入網址與 QR Code 用 `PUBLIC_BASE_URL`（例如 `https://192.168.1.23:5173`）。
  - 測試手機安裝 mkcert 的根憑證：iPhone 要在「設定 → 一般 → 關於本機 → 憑證信任設定」打開完全信任；Android 從設定匯入。步驟寫在 README。
- 備用做法：**Cloudflare Tunnel**（`cloudflared tunnel --url`）。給開發機一個暫時的 HTTPS 網址，手機不用裝憑證，也可以讓不在同一個區網的人測試；代價是流量繞經網際網路，延遲較高，**不用來測小遊戲的公平性**。
- Godot 主螢幕在開發時用 `TLSOptions.client()` 載入同一份 mkcert 根憑證，連 `wss://`。

**Godot 開發平台**

- 成員可以用 Windows 或 macOS 開發 Godot；**正式目標只有 Windows**。
- CI 在 release tag 時用 Godot 無頭模式在 Linux runner 匯出 Windows 版，並保留每次的安裝檔。
- **測試用 Windows**（2026-11-25 確認）：只用你的筆電（RTX 4060 Laptop GPU、i7-12650H、16 GB），兼開發機與主螢幕。
  - **不測低規格電腦**：已知風險是別人的舊電腦可能卡頓；灰盒測試若遇到受測者自備電腦，記錄規格與幀率。
  - 每個階段結束跑一次完整演出與 Profiler。

**測試手機清單**（2026-11-25 確認：開發期間只有 iPhone 13；Android 在灰盒測試時借受測者的手機驗證，開發期間用 Chrome 開發者工具模擬）

> 下表保留為「理想清單」；目前實際只有 #1（iPhone 13）。

| # | 類型 | 系統 | 用途 |
|---|---|---|---|
| 1 | 近兩年的 iPhone | 最新 iOS（Safari） | 主要 iOS 測試；動作感測授權流程 |
| 2 | 較舊的 iPhone | 支援範圍內最舊的 iOS ⚠️ 建議「最新版往前 2 個主版本」 | 相容性；背景斷線重連 |

- 支援範圍建議：iOS Safari 最新 2 個主版本、Android 10 以上的 Chrome 最新 2 版；範圍外顯示「建議更新」但不擋加入。
- 小遊戲公平性（M5-A02 延遲測試）只在同一個區網、mkcert 環境下測。

## 8. 最高優先級技術風險

### P0：對局中斷後無法恢復

驗收門檻（**沒通過就不進入公開 MVP**）：

```
1. 對局進行到任意事件
2. 強制終止 Server Process
3. 重新啟動 Server
4. 玩家用原 Session Token 重連
5. 重建後的狀態雜湊與中斷前完全一致
```

### P0：Godot、手機、伺服器的協定漂移

- Envelope 帶 `protocolVersion`；JSON Schema 契約測試；舊版拒絕畫面；部署順序與回滾流程。

### P0：免費主機休眠造成長局中斷

- Render Free 只用於灰盒展示；符合第 7 節任一條件就升級。

### P1：規則內容失控

- YAML 只能組合受控元件；特殊效果只能呼叫有測試的 TS Handler。

### P1：房主覆寫被濫用

- 覆寫一律新增事件、必填理由、二次確認；不改舊事件。（回滾 MVP 不做，2026-11-25）

## 9. 替代方案與切換條件

| 領域 | 定案 | 預備替代 | 何時切換 |
|---|---|---|---|
| 桌面引擎 | Godot 4 穩定版 | Unity LTS | Godot 無法穩定支援必要的 Steam、影片、輸入裝置或第三方 SDK，且自行維護成本明顯高於轉換成本 |
| Godot 語言 | 靜態型別 GDScript | C#；效能模組用 C++ GDExtension | 客戶端邏輯明顯擴大、重構需求超過 GDScript 能力；或 Profiler 證明單一工作每幀超過約 2～3 ms 且優化後仍無法改善 |
| 權威規則 | TypeScript 純函式 Reducer | Rust 或 C# 獨立核心 | 模擬量 TS 難以負荷，或需要把規則核心嵌入其他原生平台 |
| 遊戲伺服器 | Node.js＋Fastify | Go、Bun 或 Hono | 壓力測試 Event Loop 延遲 p95 持續超過 50～100 ms，且分離 CPU 工作後仍無法改善 |
| 即時通訊 | 標準 WebSocket＋ws | Socket.IO | 自建斷線恢復與房間管理的成本過高 |
| 伺服器權威位置 | 雲端 | 房主本機權威伺服器 | 雲端成本難以承擔，且產品確定只做同地聚會 |
| 手機控制器 | React＋Vite | Preact 或 Svelte | 首次載入大小或低階手機效能成為實測問題 |
| 管理後台 | React＋Vite | Godot 內建房主面板 | 後台功能很少，只供桌面房主使用 |
| 資料庫 | PostgreSQL | 離線模式用 SQLite | 單機離線版 |
| ORM | Drizzle | Kysely 或 Prisma | 團隊更重視圖形化工具（Prisma）或高度 SQL 導向（Kysely） |
| 驗證 | Zod | TypeBox＋Ajv | 驗證成為可測量的瓶頸 |
| 規則資料 | YAML＋嚴格 Schema | JSON 或內容編輯器 | 非工程人員大量編輯、YAML 錯誤頻率影響製作效率 |
| 協定 | JSON＋JSON Schema | MessagePack 或 Protocol Buffers | 頻寬或序列化 CPU 成為實測瓶頸 |
| 測試 | Vitest＋fast-check＋Playwright＋GUT | Node Test Runner、Cypress、原生 Godot 測試場景 | GUT 跟不上鎖定的 Godot 版本等 |
| CI/CD | GitHub Actions | GitLab CI 或自架 Runner | 免費分鐘長期不足；Godot 完整匯出只在 release tag 執行 |
| 日誌與監控 | Pino＋Sentry Free | OpenTelemetry＋Grafana Loki | 公開營運、多節點部署 |
| 正式伺服器 | 單節點常駐付費主機 | 雙節點房間分片 | 同時房間數、營收或 SLA 足以支撐高可用成本 |

**替代方案的啟用順序**：先設定、測試與優化現有技術 → 只替換單一可隔離元件 → 引入相容層並平行驗證 → 最後才做平台或語言遷移。

## 12-3 主螢幕斷線（2026-11-24 確認：自動暫停等重連）

| 項目 | 規則 |
|---|---|
| 判定 | 主螢幕心跳逾時 **10 秒**（玩家維持 15 秒）即判定斷線 |
| 暫停 | 伺服器送出系統命令，產生 `game.paused`（`reason: host_disconnected`）；進行中的小遊戲照常打完並結算，結算後才進入暫停 |

## 12-5 機率與信任（2026-11-25 確認）

| 項目 | 規則 |
|---|---|
| 種子產生 | 開房時用密碼學亂數（`crypto.randomBytes(32)`，在伺服器、不在引擎裡）產生 256 位元對局種子；之後所有亂數都由它衍生。資料庫欄位 `matches.seed` 用 `bytea`，對局結束前只有伺服器與 admin 讀得到 |
| 演算法 | **ChaCha20**（RFC 8439），在 `packages/rules-engine/src/rng/` **自己實作**（約 60 行，不新增執行期依賴），以 RFC 8439 官方測試向量驗證；同一份程式也匯出給 `packages/protocol`，讓手機用同一套產生小遊戲題目（2026-11-25 確認） |
| 獨立亂數流 | 流名稱：`map`、`deck.minor`、`deck.trial`、`deck.nether`、`deck.major`、`orientation`、`dice`、`loot`（開局魔術骰子、商城、拍賣品、隨機道具）、`casino`、`minigame`、`bot`、`presentation`（軌跡與近失）、`misc`（隨機配對等）。每條流的金鑰＝HMAC-SHA256（種子, `"fate-tavern/v1/"`＋流名稱） |
| 依索引取用 | 同一條流內**依索引取亂數，不依順序**（2026-11-25 確認）：每一次「取亂數的事件」有自己的索引（第 N 次擲骰、第 N 輪洗牌、第 N 張抽牌的正逆位、第 N 場小遊戲…），以索引當 ChaCha20 的 nonce、從區塊 0 開始取；同一事件需要多個數字時，在該事件內往下取。某個效果多擲一次骰，只影響那一次，不會讓後面的結果位移。各流的「下一個索引」存在遊戲狀態內 |
| 整數與機率 | `int(min,max)` 一律用**拒絕取樣**（禁止直接取餘數，除非範圍是 2 的次方）；洗牌一律用 **Fisher–Yates**；機率一律用整數（正逆位 70/30 寫成 `int(1,100) ≤ 70`；稀有度用累積整數權重），不用小數比較 |
| 回滾（MVP 不做，之後加入時照此） | 回滾會把亂數索引一起還原，**重做同一動作會得到同一結果**；回滾不是重抽（可以防止用回滾重擲），後台畫面要提示 |
| 小遊戲題目 | 題目種子＝`minigame` 流第 N 場的輸出，隨 `minigame.start` 才送到手機（不在 `prepare` 先送），縮短提前計算答案的時間（2026-11-25 確認）；被改過的手機程式仍可能即時算答案，這部分靠合理性檢查與現場監督 |
| 牌庫 | 小牌、試煉、冥界、大牌各一副，開局用各自的 `deck.*` 流洗牌，抽完重洗也用同一條流；規則見《設定總表》第 5 節「牌庫與抽牌」 |
| 盲選 | 手機送出選的是第幾張（位置 0～3），伺服器依當下牌序決定是哪張牌；牌序只在伺服器，客戶端拿不到 |
| 種子承諾 | `game.started` 帶 `seedCommitment`＝SHA-256（種子＋對局 ID）；主螢幕開局畫面顯示前 8 碼。`game.ended` 公布種子，結算畫面顯示 |
| 驗證（MVP 不做，2026-11-25 簡化後端；種子承諾保留） | 對局結束後可以匯出「對局驗證檔」（種子、全部命令紀錄、最終狀態雜湊）；`tools/replay verify` 檢查種子雜湊與承諾一致、重播後最終雜湊相同。覆寫與回滾本身就是公開事件，驗證檔會列出 |
| 測試 | 分布檢定：D4、D6、D8、D12、D20 各 10 萬次卡方檢定；洗牌 10 萬次檢查每張牌在每個位置的次數；正逆位、稀有度比例（M4-A02、M6-A01）；ChaCha20 通過 RFC 8439 測試向量；流獨立與索引獨立（M1-A13、M1-A15） |
| 測試控制 | `admin.test_control`（指定下一張牌、下一個骰點）只能在**測試模式**的對局使用；正式對局一律拒絕 |
