# 00｜階段總覽與共通完成定義

> 依《命運酒館_技術規劃》第 12 節的 M0～M8。每個階段一份文件：`M0_骨架與合約.md` … `M8_房主工具與灰盒版.md`。
> 需求編號格式：`M{階段}-R{序號}`（例如 `M1-R03`）；驗收條件：`M{階段}-A{序號}`。PR 標題與 commit 都要帶需求編號。

---

## 1. 階段依賴

```
M0 骨架與合約
 └─▶ M1 權威地基（事件儲存、快照、重播、崩潰恢復）  ← 閘門：沒過不能進 M2
      └─▶ M2 規則核心（回合、擲骰、移動、地圖、清醒值）
           └─▶ M3 效果系統（效果元件、反應鏈、傷害、死亡）
                ├─▶ M4 卡牌內容
                ├─▶ M5 小遊戲（可與 M4 平行）
                └─▶ M6 經濟系統（可與 M4、M5 平行）
                     └─▶ M7 職業與勝負
                          └─▶ M8 房主工具與灰盒版
```

## 2. 角色

| 代號 | 角色 | 主要負責 |
|---|---|---|
| A | 後端／規則 | `rules-engine`、`protocol`、`content`、`server`、`database`、模擬、重播、恢復 |
| B | 網頁前端 | `mobile-web`、`admin-web`、小遊戲、時鐘校正、i18n、E2E |
| C | Godot／美術 | `godot-client`、演出、2.5D 場景、局部 3D、音效、GUT |

> **2026-11-25 實際人員**：A、B 與 C 的框架部分（Net、Store、Clock、Presenter、GDScript 協定類別、GUT）＝**你**（兼職，每週約 20 小時）；C 的場景、演出、特效、骨架動畫、3D 模型、美術＝**小黃**。下文的「A／B／C」照此對應；需要「另一位成員」核准的地方，改成「兩個 AI 審查＋你核准」（審查流程 §3）。

## 3. 每個階段文件的固定結構

1. 目標與範圍（範圍內／範圍外）

## 4. 共通完成定義（Definition of Done）

每個需求都要滿足：

- [ ] 對應的驗收條件全部通過。
- [ ] `pnpm typecheck && pnpm lint && pnpm test` 通過；Godot 相關另跑 GUT。
- [ ] 新增的協定訊息有 Zod 定義＋合法／不合法範例＋重新產生的 GDScript 類別。
- [ ] 規則變更有引用設計文件章節的單元測試。
- [ ] 沒有違反 `AGENTS.md` §3 架構邊界與 §4 硬性禁止。
- [ ] PR 依模板填寫，經另一個 AI 工具審查、人類核准。
- [ ] 沒有新增未經 ADR 的執行期依賴。
- [ ] 顯示文字都走語系鍵。
