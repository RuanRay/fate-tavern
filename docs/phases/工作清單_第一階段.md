# 命運酒館｜工作清單（第一階段）v1.0

> 更新日期：2026-11-25（v1.0：定案，確認紀錄見第 5 節）
> 用途：把第一階段（核心可玩版，M0～M7a）的需求拆成**一次交給 AI 一個**的任務，標好順序、依賴、大小與審查等級。你每週約 20 小時，照「下一個沒被擋住的任務」往下做。
> 依據：各階段文件（`docs/phases/M*.md`）、《技術規劃》§12-1、《遊戲狀態模型》、《設定檔總表》、《訊息欄位表》、《文字版主螢幕》、《審查流程》§3。
> 細拆程度：**M0、M1 細拆到任務**；M2 以後先拆到「需求組」並給工時，**每個里程碑開工前一週再細拆**（B1）。

---

## 0. 欄位與規則

| 欄位 | 說明 |
|---|---|
| 任務 ID | `T-M0-01` 格式；PR 標題與 commit 帶任務 ID 與需求 ID |
| 需求 | 對應的 `M?-R??`（多個用頓號） |
| 依賴 | 必須先合併的任務；沒有寫＝可以直接開始 |
| 工時 | 你的實際時間（含規劃、審查、修正；不含 AI 自己跑的時間）；**單一任務 ≤ 8 小時**（B3），超過就拆 |
| 審查 | 🔴／🟡／🟢，照《審查流程》§3：🔴 兩個不同 AI 審查＋你隔天再看一次 diff |
| 驗收 | 對應的 `M?-A??`；沒有對應的寫「單元測試」 |

- 里程碑的工時預算（技術規劃 §12-1）已含 20% 緩衝；本表的任務工時合計約為預算的 85%，剩下的是緩衝。
- 進度在 **GitHub Issues＋Projects 看板**追蹤（B2）；本表是規劃來源，Issue 由 `tools/backlog` 從本表產生（B4）。每週結束看一次看板；連續兩週實際工時超過估計 50% 以上，就重估該里程碑。

## 1. 每週工作方式

```
1. 從本表挑「依賴都已合併」的下一個任務（同時最多 2 個進行中）
2. 對應的 Issue 已由 `tools/backlog` 建好（每個里程碑開工時跑一次）；確認內容後指派給自己
3. 用提示詞範本 §1 交給實作 AI → 先拿計畫 → 你確認 → 測試先行 → 實作
4. 開 PR → CI 全綠 → 審查 AI（🔴 再加第二個 AI）→ 處理意見
5. 你核准合併（PR 寫 `Closes #<Issue>` 自動關 Issue）；在 Issue 填實際工時
```
