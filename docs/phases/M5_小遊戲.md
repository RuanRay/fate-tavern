## 4. 技術細節

### 4-1 手機端結構

```
apps/mobile-web/src/minigames/
├─ framework/        共用：倒數、計時（伺服器時間換算）、輸入紀錄、上傳
├─ tug-of-war/  quick-draw/  rune-spotting/  drink-order/  forging/
├─ stopwatch/   rune-rps/    chicken/        coin-count/
└─ registry.ts       gameId → 元件
```

- 每個小遊戲是獨立模組，介面：`mount(container, prepare, clock, send) → unmount`。
- 題目由 `seed` 產生，產生函式放在 `packages/protocol` 共用（伺服器重播與驗證也用同一份）。

### 4-2 公平性

- 反應類比的是「本地時間差」：從手機畫面真正顯示訊號的那一幀（`requestAnimationFrame` 時間）到觸控事件時間。
- 伺服器用延遲模擬測試（100～300 ms 抖動）確認結果不受網路影響。

## 6. 驗收條件

| ID | 條件 |
|---|---|
| M5-A01 | 9 種小遊戲在 iOS Safari 與 Android Chrome 實機可玩，從開始到結果 ≤ 15 秒（不含準備） |
| M5-A02 | 兩支手機網路延遲差 250 ms 時，拔劍決鬥結果只取決於反應時間 |
| M5-A03 | 同一場的所有參加者題目完全相同（種子一致），重播能重現題目 |
| M5-A04 | 二對一時單人分數 ×1.5 由伺服器套用，手機端看不到也改不了 |
| M5-A05 | 送出偽造的超快反應（< 50 ms）被標記可疑並記入遙測 |
| M5-A06 | 主螢幕觀戰畫面與手機同步，拔河繩子延遲 < 300 ms |
| M5-A07 | 每種小遊戲都有「平手 → 加賽 → 系統擲」的測試；加賽時間 ≤ 5 秒 |
| M5-A08 | 竄改手機回報分數（例如數金幣送出正確答案但 `inputLog` 沒有作答紀錄），伺服器以重算結果判定並記入遙測 |

## 7. 測試要求

- Playwright：多分頁模擬參加者，跑完 9 種小遊戲的完整流程。
- 單元：題目產生器（同種子同結果）、計分、二對一、戰吼加成。
- 延遲模擬：在 WebSocket 層注入延遲與抖動。

## 8. 審查重點

- 勝負是否完全由伺服器判定（手機只回報分數與紀錄）。
- 計時是否都用伺服器時間換算。
- 是否在手機端洩漏其他人的私人資訊。

## 9. 限制與禁止

- 小遊戲時間不得超過 15 秒（不含 3 秒準備）；平手加賽另計，每次 ≤ 5 秒。
- 不准讓清醒值影響小遊戲（設定總表 §4）。
- 不准在手機端計算最終勝負或套用係數。

## 10. 風險

| 風險 | 對策 |
|---|---|
| 低階手機掉幀影響反應類 | 量測幀時間；PixiJS 場景保持簡單 |
| 二對一 ×1.5 對記憶、猜拳類不公平 | 係數放設定檔，灰盒逐款調整（設定總表 §7 ⚠️） |
